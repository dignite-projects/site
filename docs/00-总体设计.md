# Dignite Site — 总体设计

> 本文是 Dignite Site 的**权威设计文档**，取代早期分散的 6 篇讨论稿（架构对标 / 领域模型 / SEO 规划 / 技术选型 / 演进策略 / 开放式前端）。定位、概念模型、站点能力、前端与选型均以本文为准。
>
> **进度：P0 内容内核已落码**（见 §9 路线图）。Page / ContentType / Content / Field 四实体、FlexFields 接线、多租户、多语言与路由解析（§3.4）已实现并有测试覆盖；P1 起尚未开始。

## 1. 定位与核心理念

### 1.1 是什么

Dignite Site 是**多租户站群平台**，是 **Dignite.Cms 的 AI 原生下一代**，跑在 ABP 之上。它保留 Cms 已验证的 DNA——字段定义、多租户、多语言、版本化——把内容的**录入接口从"后台表单"换成"用户自己 AI 客户端里的 MCP"**，并补齐 Cms 缺失的站点层（SEO / sitemap / feed / 域名）。

产品名 `Site`（单数）= 每个租户对应的那一个站点；"这是多租户产品"这件事由 `Dignite.` 前缀与租户机制本身表达，不需要包名再复数化（§4.3"一租户一站点"）。

### 1.2 三个核心理念

**① 一切皆 page，page 即路由。**
页面的第一职责是路由。即使外部前端自带路由，后端的 page 集合仍然是**权威路由表**——因为 sitemap、canonical、hreflang 这些站点级产物全部从它派生。这是 page 存在的根本理由。

**② AI 通过 MCP，平台不做后台助手。**
平台**不内嵌** AI 助手。差异化在于把平台能力开放为 **MCP**，智能在用户自己的 AI 客户端里：用户口述"建一个页面，路由是 xx，内容是 xx"或"发一条新闻（粘贴正文）"，AI 客户端调 MCP 工具，平台按字段定义校验、入库，路由与 sitemap 自动更新。建站期与运维期都是这一条路径。

**③ schema 即契约。**
字段定义既是内容写入的**校验闸门**，也是喂给 AI 的**目标形状**。这是从早期 flat-file 调研里保留下来的最有价值的一条理念——尽管内容存储最终定回了数据库，这条理念独立成立。

### 1.3 与传统 CMS 的差异

传统 CMS 让用户在后台手填表单。Site 把这套能力开放成 MCP，用户在客户端口述完成建站与日常运维。**原有架构（字段定义、条目、版本化、多租户）全部保留**，变的只是"谁来写、怎么写"。

MCP 优先不排斥将来平台自己再内嵌助手，两者不冲突；但那不是当前目标。

### 1.4 存储决策（已定）

内容以**数据库**为事实来源，沿用 Dignite.Cms 已验证的"字段定义 + 条目 + 版本化"内核。

> 早期文档提出的"文件（md + frontmatter）为唯一事实来源、EF 只存可再生索引"方案**已废弃**。理由：一旦主流程变成 MCP 直写，flat-file 的最大卖点（Git 分支 / PR 人审 / 天然版本化 / 可移植）大幅缩水，而其代价（每租户可写存储、索引重建、并发写入）一个不少。Git / PR / 版本化 / 可移植是**前端模板与代码**层面的事，与内容层无关。

### 1.5 适用边界

展示型 / 内容型站点——新闻、页面、博客、产品展示，这是本方案的主场。一旦进入事务 / 交互逻辑（购物车、库存、订单），另上后端 + 关系库，不硬套。CMS 本就服务于展示层，这条边界要守住。

### 1.6 命名（已定）

项目定名 **`Dignite.Site`**，包名线 `Dignite.Site.*`（Domain / Application / Application.Contracts / EntityFrameworkCore / HttpApi / Web）。

- **不叫（回）Cms**："Management System" 自带"后台"心智，正是本项目背离的方向（后台表单 → MCP 口述）；且需与上一代 `Dignite.Cms`（进维护模式）清晰区隔——换名才说得清"这是换代不是升级"。
- **选 Site（单数，非 Sites）**：成果导向（用户做出的是一个网站）；一租户一站点是钉死的结论（§4.3），`Site` 本身已不是领域实体、只是租户设置的集合（§4），复数没有对应的聚合或场景可挂——sitemap / 域名 / SEO 本就是 site 层面能力，"泛"由 `Dignite.` 前缀消解。（曾认真考虑 `Pages`——扣"一切皆 page"理念——但它在 web 圈已被 GitHub/Cloudflare Pages 占成"静态托管"心智，弃。）
- **AI 不进包名**：AI 是当前最强手段而非产品的持久本质（避免像 "Cloud xxx" 那样过时）。AI 原生放在副标题 / 仓库描述：*AI-native, MCP-first multi-tenant site platform for ABP*。

> **命名修正**：项目最初定名 `Dignite.Sites`，类前缀沿用复数（`SitesSettings`、`SitesPermissions` 等），类比 GitHub/Cloudflare Pages——但那两者的复数成立在于"一账户建多个站点"，本项目从一开始就是"一租户一站点"（§4.3），且 Site 从未作为可以成群的实体存在过（§4 移除了 `Site` 聚合根）。复数在这里没有对应的领域事实，读起来别扭是这个原因，不是错觉。已改名 `Dignite.Site`，命名空间 / 类前缀 / csproj / 目录全仓库同步重命名。

## 2. 概念模型（核心）

### 2.1 三个核心实体

整个模型收敛为三个核心实体，正好对应"page / 字段 / 内容"，再加一张**独立的字段定义表**作为支撑，**整套结构对齐 Dignite.Cms 已验证的成熟模型**：

| Site | ≈ Dignite.Cms / Craft | 是什么 | 一句话职责 |
|---|---|---|---|
| **Page** | Section | 路由节点 | 这个 URL 存在、下面有哪些内容类型、用什么模板 |
| **ContentType** | EntryType | 内容类型 | **隶属于某个 Page**，编排一组字段，定义"这种内容长什么样" |
| **Content** | Entry | 内容记录 | 按某个内容类型、落在某个路由下的一条数据 |
| **Field** | Field | 字段定义（独立表） | **租户级字段库**，一次定义、被多个 ContentType 复用 |

**三层归属链**：`Page → ContentType → Field`（引用），内容落在 `Content(PageId, ContentTypeId, 各字段值)`。ContentType 隶属 Page、不跨 page 共享；**复用发生在字段层**——同一个 Field 可被任意多个 ContentType 引入。

配置（域名、语言等）**不是实体**，见 §4；站点级能力（sitemap 等）是**派生产物**，见 §5。

### 2.2 Page（路由节点）

| 属性 | 说明 |
|---|---|
| **Route** | 核心属性。路由模板，不是单纯的基础路径。纯字面即无下辖内容（`/about`、`/`）；`{slug}` 即其下内容都必须有别名（`/blog/{slug}`），`{slug?}` 则额外允许一条别名为空的默认内容；要日期段就 `{publishTime:yyyy-MM}/{slug}`（占位符可以是任意字段名，不是凭空发明的关键字，对齐 Dignite.Cms）。页面自身地址 = Route 中第一个 `{` 之前的最后一个完整路径段，纯字面 Route 地址就是它本身（见 §3.3） |
| **下辖的 ContentType** | **一对多隶属**：ContentType 建在 page 之下（外键 `PageId`），一个 page 可以承载多种形态的内容（见 §2.6 例子） |
| **Template** | 可选。渲染模板引用。仅在需要后端点名视图的前端模式（MVC catch-all）下用；Razor Pages / 外部前端自带渲染则用不到（见 §7） |
| 首页判断 | 非独立字段：Route 自身地址（见上）落在 `/` 即为首页（`PageRoute.IsHomeRoute`），和"有没有下辖内容"同一套"不设存储标志位、从 Route 读出"的逻辑；Status——聊导航时再细化 |
| **ParentId** | 可空自引用，Admin 后台把 page 组织成父子孙树用的**纯组织字段**——不影响 Route，路由解析不看它；一个子 page 可以有和父级路由毫无关系的 Route。主页永远是根（Route 落在根路径时会静默清空 ParentId）；有子 page 时拒绝删除，不级联 |

Page **不预设 Kind**（单页 / 列表 / 详情不区分）、**不含字段定义**、**不挂 SEO**。它就是纯路由 + 下辖的类型 + 渲染提示。Route 与内容路径模式合并成单一字段后，`{slug}` 的有无就是"这个 page 下有没有内容"唯一且隐式的信号——没有照搬 Dignite.Cms 那条"非单页必须含 `{Slug}`"的强制校验，因为 Cms 靠 `SectionType` 判断，Site 没有 Kind 可依据。

### 2.3 ContentType（内容类型）与 Field（字段库）

字段定义**不内联在 ContentType 里**，而是独立成表。这是与 Dignite.Cms 一致的做法，两者职责分开：

- **Field = 字段"是什么"**——租户级字段库里的一份独立定义，与用在哪儿无关。
- **ContentType = 字段"怎么编排"**——隶属某个 Page，从字段库里挑一组字段组装成一种内容形态。

#### Field（独立定义表，租户级）

**Field 实现 `Dignite.Abp.FlexFields` 的 `IFlexField` 契约**（见 §8.2），属性与之一一对应：

| 属性 | 对应 `IFlexField` | 说明 |
|---|---|---|
| **Name** | `Name` | 租户内唯一标识，如 `title`、`body`、`cover`。**同时是值袋里的 key**——故改名是一次数据迁移，见 §2.4 |
| **DisplayName / Description** | 同名 | Description 同时是给 AI 的字段说明 |
| **FieldTypeName** | `FieldTypeName` | 字段类型的注册名，见下 |
| **Configuration** | `Configuration` | 类型特有配置（字符上限、可选项、媒体约束等），`FieldConfigurationDictionary` |
| **Group** | —（Site 自有） | 可选。字段库的组织分组（≈ Cms `FieldGroup`），纯管理用途，不影响运行时 |

字段类型由 **FlexFields 内核的 `IFieldType` 提供**，内置六种（Text / Number / DateTime / Select / Boolean / Tree），Site 按需自注册扩展类型（richtext / media / reference / list 等）——注册走 DI，不改内核。每个 `IFieldType` 自带 `IndexValueType`（`String / Number / DateTime / Boolean / Guid`，`null` = 该类型不可索引，如富文本），决定值落进查询索引的哪个类型化列，见 §2.4。

> **注**：字段类型抽象**不自建**。早期曾规划由 Site 自己抽一层字段类型抽象（把 DynamicForms 验证过的模式吸收过来重写）——那层现已独立成 `Dignite.Abp.FlexFields` 模块并落码，Site 直接消费即可。详见该模块的 `docs/flexfields-design.md`。

**一次定义、处处复用**：`title` 只在字段库里定义一遍，博客帖子、产品、新闻的 ContentType 都引入同一个 Field。改一处，所有引用它的类型同步——这正是独立定义表相对内联字段的核心价值。

#### ContentType（隶属 Page 的字段编排）

| 属性 | 说明 |
|---|---|
| **PageId** | **隶属的 Page**（≈ Cms `EntryType.SectionId`）。ContentType 建在 page 之下，不跨 page 共享 |
| **Name** | page 内唯一，如 `post-article`、`post-gallery`、`post-video` |
| **DisplayName / Description** | Description 同时是给 AI 的类型说明 |
| **引入的字段[]** | 有序引用列表，每项指向字段库里的一个 Field，见下 |

**引入的字段项**（≈ Cms `EntryField`）= 一个 `FieldId` 引用 + **本类型内的"用法"属性**：

| 用法属性 | 对应 | 说明 |
|---|---|---|
| **Required** | Cms `EntryField.Required`；FlexFields `FlexFieldValue.Required` | 本类型下该字段是否必填 |
| **Searchable** | Cms `EntryField.EnableSearch`；FlexFields `FlexFieldValue.Searchable` | 本类型下该字段的值是否拆解进查询索引表（见 §2.4） |
| **ShowInList** | Cms `EntryField.ShowInList` | 列表场景是否呈现该字段 |
| **DisplayName**（可选覆盖） | Cms `EntryField.DisplayName` | 不填则用 Field 自身的显示名 |
| **Order** | —（Cms 靠 Tab 内集合顺序，Site 去 Tab 后显式给序号） | 在本类型内的顺序 |

> **为什么这些挂在引用上而不是 Field 上**：Field 描述字段的**固有性质**（类型、配置），跨类型恒定；Required / Searchable / 顺序 / 显示名描述的是**这次使用的意图**，天然随类型而变——同一个 `title` 在 `post-article` 必填可搜、在别处选填不索引，都正常。这既是 Cms `EntryField` 的切法，也正是 FlexFields `FlexFieldValue` 的切法（其 XML 注释明写 *"Per-usage rather than per-definition"*）。两边一致，沿用。

ContentType **不含路由、不含模板、不含基数标志**——那些是 Page 的事或运行时决定。它可以**引入一组标准 SEO 字段**（见 §5.3）。

> **与 Cms 的唯一差异：不设 `EntryFieldTab`。** Cms 里 EntryType 的字段先分 Tab 再列字段，那是后台表单的 UI 分组——Site 主路径是 MCP、弱化后台表单，这层分组失去所指，且它让"类型有哪些字段"要穿两层集合才拿得到。ContentType 直接持有扁平的字段引用列表。已定。（FlexFields 内核对此无所谓：富页签布局本就归下游 UI。）

### 2.4 Content（内容记录）

一条内容 = **`PageId` + `ContentTypeId` + `CultureName` + 各字段的值**——结构完全对齐 Cms `Entry`（`SectionId` + `EntryTypeId` + `Culture` + 字段值），仅语言列改名，理由见下。**一条 Content 就是一个语言的一条记录**，多语言 = 多行。

- **归属 Page**：决定它落在哪条路由下、URL 前缀是什么。
- **归属 ContentType**：决定它有哪些字段、渲染成哪种形态。
- **两个归属都显式持有**：`PageId` 虽可从 `ContentTypeId` 推导（ContentType 已隶属 Page），但仍冗余存一份——按 page 拉内容是最高频查询（列表页、sitemap、路由解析），不该每次都绕一跳。Cms 的 `Entry` 同样两个都存，沿用。
- **系统字段有四个**：`CultureName`（本行是哪个语言）、`Slug`（路由解析的 key）、`status`（草稿 / 发布 / 归档）、`PublishTime`（发布时间，与 status 配合实现**定时发布**——约束 `Draft` 不允许配未来的 `PublishTime`，定时发布即直接存为 `Published` + 未来 `PublishTime`；可见性由读路径统一的 `PublishTime <= now` 过滤兜底，无需后台作业按时翻转状态）。加 ABP 审计字段（创建 / 修改时间与人，自动带）。
- **业务字段**：全部来自其 ContentType 引入的 Field——包括 Title、SEO、正文，一切展示性数据。值全部落在本行自己的值袋里（见下），**不存在"跨语言共享的字段值"**：非本地化字段在各语言行里各存一份。
- **多语言分组靠自然键，不设分组 Id**（已定）：`(PageId, ContentTypeId, Slug)` 相同、`CultureName` 不同的若干行，**天然就是同一条内容的各语言版本**。hreflang（§5.5）与语言切换直接按这个自然键聚合派生，无需额外的 `TranslationGroupId`——Cms 没有分组机制，Site 也不加。

> **代价要认**：分组键含 `Slug`，等于**要求同一条内容的 slug 跨语言一致**（`/en/blog/my-trip` 与 `/zh/blog/my-trip`），不能给中文版单独起一个本地化 slug。换来的是零额外实体、零额外外键，分组关系永远不会与数据脱节。

#### 语言列为什么叫 `CultureName`（已定）

Cms 叫 `Entry.Culture`，Site 改叫 `Content.CultureName`。这是**唯一一处对 Cms 结构的命名修正**，理由三条：

- **对齐 ABP 自己的先例**：`Volo.Abp.LanguageManagement.Language` 实体的字符串属性就是 `CultureName` / `UiCultureName`。ABP 的模式是"概念叫 Language，存字符串的属性叫 CultureName"。Site 的语言清单本就从 ABP 设置 / LanguageManagement 读，同名 = 读出来直接用，零转换。
- **类型诚实**：它是 `string`，装的是 `CultureInfo.Name` 的值，不是 `CultureInfo`。裸叫 `Culture` 在 .NET 里读起来像是后者——ABP 凡存字符串处一律加 `Name` 后缀正是为避此歧义。
- **不与 ABP `Language` 实体撞名**：若叫 `Content.Language`，同一解决方案里它是 string、`Language` 却是聚合根，读代码时容易错位。

**值域约定（硬约定）**：存 **`CultureInfo.Name` 形式的 BCP 47 标签**——`en`、`zh-Hans`、`en-GB`，大小写与分隔符严格照 .NET 的规范形式。

> 这条必须钉死：同一个值同时充当 **URL 前缀**、**hreflang 属性值**和**唯一键与分组键的一部分**，三者对格式的容忍度不一样。一旦出现 `zh-CN` 与 `zh-cn` 各存一行，唯一约束拦不住（多数排序规则下二者不等），分组就会从中间裂开，hreflang 随之输出两组互不相认的链接。写入口（MCP / 后台）统一过 `CultureInfo.GetCultureInfo(x).Name` 规范化后再落库。

> **系统字段 vs 业务字段的划分标准**：系统字段 = 平台机制**铁依赖**、不可能交给业务自定义的（Slug 支撑路由、status 支撑发布流程、PublishTime 配合 status 支撑定时发布）；业务字段 = 展示性数据（Title、SEO……）。凡是"某个类型需要、另一个类型不需要"的，都归业务字段。

#### 值怎么存：FlexFields 的 Y 方案（已定）

字段值**不自建存储方案**，直接采用 `Dignite.Abp.FlexFields` 已落码的 Y 方案（见该模块 `docs/flexfields-design.md` §4）。它是**权威值袋 + 派生索引表**两层：

| 层 | 落在哪 | 职责 |
|---|---|---|
| **权威值袋** | Content 实体自己的 `FlexFields` 字典列（`Content : IHasFlexFields`） | 唯一事实来源。整条内容读取只查这一处，一次拿全 |
| **派生查询索引** | 独立的 `ContentFlexFieldIndex` 表（Site 自有，继承内核的 `FlexFieldIndexBase<Content>`） | 只为"找出字段 X 匹配 Y 的内容"能走 SQL 而非内存过滤 |

**权威值袋**是 FlexFields 自建的 `FlexFieldDictionary`，**不是 ABP 的 `ExtraProperties`**——刻意与公共大袋子隔离，防撞名、平台自持。

- **袋子的 key 是 `Field.Name`**（不是 Id）。所以**字段改名是一次数据迁移，不是一次简单编辑**：内核给了 `IFlexFieldValueMigrator<Content>`（provider 中立、唯一实现、下游零代码），改完定义后调 `RenameFieldAsync(oldName, newName)` 重写袋子 key。删字段同理。
- **索引行的键是 `FieldId`**（不快照字段名）——所以纯改名对索引无害，索引不需要跟着迁移。两层的键刻意不同，这是设计的一部分。

**派生索引表**每宿主类型一张，Site 只需要 `ContentFlexFieldIndex` 一张：

- 行结构 = `FieldId` + `ValueType` + **五个类型化槽位**（`StringValue` / `NumberValue` / `DateTimeValue` / `BooleanValue` / `GuidValue`）+ Site 自己声明的 `ContentId` 外键。数字进数字列、日期进日期列，**不 stringify**，比较走原生类型。
- **只索引 `Searchable` 的用法**（§2.3 引用行那个开关）；字段类型的 `IndexValueType` 为 `null` 者（如富文本）根本不可索引。
- **写时同 UoW 同步**：值一变，索引在同一个事务里跟着更新，不存在读到陈旧索引。
- 查询路径：条件 → 索引表 → `ContentId` → 回宿主过滤。`FlexFieldQueryCondition` 自带 `ValueType`，查询侧自描述、不回查定义。
- `Searchable` 翻开 / 字段类型改动都只需 `RebuildAsync` 全量重推——索引每次都从袋子里的原始值重新解释，没有独立的值迁移。

> **这一步直接治掉了 Cms 的老毛病**：Cms 的值存在 `ExtraProperties` JSON 里，`EfCoreEntryRepository.GetListAsync` 一旦带自定义字段条件就 `AsEnumerable()` 拉进内存过滤，数据量一大就是全表扫。类型化索引表让同样的查询回到 SQL 侧走索引。

> **provider 中立**：上述透视表形状只属于 `FlexFields.EntityFrameworkCore`。若将来走 MongoDB，内核直接在值袋上建原生路径索引、无透视表，写时近乎零同步——Site 这一层的设计不用改。

### 2.5 关系与约束

- **Page → ContentType**：一对多**隶属**（ContentType 持 `PageId`）。类型建在 page 之下，删 page 即连带其类型；**类型不跨 page 复用**。
- **ContentType → Field**：多对多**引用**（经引用行，带 Required / DisplayName / Order 覆盖）。一个 Field 可被任意多个 ContentType 引入——**跨 page 的复用只发生在这一层**。
- **Content → (Page, ContentType)**：双重归属，各指一个；两者必须自洽（`Content.PageId` == 其 `ContentType.PageId`）。
- **Field → 值**：权威值按 **`Field.Name`** 存在 Content 的值袋里（故改名要迁移）；派生索引行按 **`FieldId`** 关联（故改名不影响索引）。两层键不同是刻意的，见 §2.4。
- **唯一约束**：`(租户, PageId, CultureName, Slug)` 唯一——同一 page 下、同一语言、slug 不重复（对齐 Cms 的 `SlugExistsAsync(culture, sectionId, slug)`）。
- **多语言分组**：`(PageId, ContentTypeId, Slug)` 相同、`CultureName` 不同 = 同一条内容的各语言版本。**自然键分组，不设分组 Id**；代价是 slug 跨语言一致，且 `CultureName` 必须规范化存储，均见 §2.4。
- **Page → Page（ParentId）**：自引用，可空=顶级。**纯组织关系，与 Route 无关联**——不像 ContentType/Content 那样是领域上的隶属，只是 Admin UI 呈现层的树形分组。删除有子 page 的 page 会被拒绝（不像 ContentType/Content 那样级联），因为子树各自可能挂着自己的 ContentType 和 Content，级联下去的破坏半径不可控。

### 2.6 一个完整例子

一个公司官网：首页 + 关于我们 + 博客（帖子分图文 / 相册 / 视频三种形态）。

**① Field（字段库，租户级——先定义一次，后面反复引用）**

| Field | 类型 | 说明 |
|---|---|---|
| `title` | text | 标题 |
| `body` | richtext | 正文 |
| `cover` | media | 封面图 |
| `gallery` | list | 图集（多图） |
| `video-url` | text | 视频地址 |
| SEO 字段组 | 预设的一组 | 标准 SEO 字段组预设，见 §5.3 |

**② Page → ContentType（类型建在各自 page 之下，从字段库引入字段）**

| Page | Route | 下辖 ContentType | 引入的字段 |
|---|---|---|---|
| 首页 | `/` | `home` | `title`、`body`、`cover` |
| 关于 | `/about` | `about` | `title`、`body` |
| 博客 | `/blog/{slug}` | `post-article` | `title`、`cover`、`body` + SEO 组 |
| | | `post-gallery` | `title`、`cover`、`gallery` + SEO 组 |
| | | `post-video` | `title`、`cover`、`video-url` + SEO 组 |

注意 `title` / `cover` / `body` 在五个类型里**是同一个 Field**，各自只在引用上设不同的 Required 与顺序。想给全站标题加个字符上限，改字段库那一处即可。三个博客类型都隶属 `/blog` 这个 page，不会（也不需要）被别的 page 借用——**跨 page 复用的是字段，不是类型**。

**运行时 URL**
- `/` → 首页 page 下那条 `home` 内容 → 前端渲染单页
- `/about` → 关于 page 下那条 `about` 内容 → 单页
- `/blog` → 博客 page 本身 → 前端渲染列表（自己拉它下面的内容）
- `/blog/my-trip` → 博客 page 下 slug=my-trip 的内容 → 前端按它的 ContentType（比如 `post-gallery`）选相册模板渲染详情

新增一条博客内容并发布，它的详情 URL 自动出现、sitemap 自动收录——不需要动任何 page。这就是"一切皆 page"和"page 即路由"的兑现。

## 3. 路由与 URL

### 3.1 Page 是权威路由表

后端的 Page 集合（连同其下 Content 的 slug）就是这张路由表：行是运行时数据，用户 / AI 新增一条内容即新增一条路由，无需重新编译或重启。前端就算自带路由，这张表也必须在后端存在——sitemap / canonical / hreflang 都从它算。

### 3.2 URL 构成

**URL = 把内容代入 page 的路由模板（Route）；slug 为空则退化为模板的"页面自身地址"部分**（推导规则见 §3.3）。单页和列表由此统一，不需要 Kind：

| URL | 解析 | 前端渲染成 |
|---|---|---|
| `/about` | `about` page 下那条 slug 为空的内容 | 单页 |
| `/blog` | `blog` page 本身（Route 为 `/blog/{slug}` 时，`/blog` 是它的自身地址） | 列表 |
| `/blog/my-post` | `blog` page 下 slug=my-post 的内容 | 详情 |

### 3.3 路由模板

Route **本身就是模板**，不是另一个独立字段拼出来的：
- 纯字面、不含 `{slug}`/`{slug?}` → 这个 page 没有下辖内容，如 `/about`、`/`；
- 含 `{slug}` → 其下**每条**内容都必须有别名，如 `/blog/{slug}` → `/blog/my-post`；
- 含 `{slug?}` → 同样解析其下内容，但额外允许一条别名为空、落在页面自身地址上的默认内容——`/about/{slug?}` 下 `/about` 是默认内容，`/about/history` 是带别名的内容。两者互斥，一个 Route 不能同时出现。

`{slug}`/`{slug?}` 的有无、以及二者的取舍，是"这个 page 下能不能有内容、别名能不能留空"唯一且隐式的信号，不再有另一个字段去声明它，也没有隐式默认——不写就是真没有下辖内容，不会偷偷补上。这属于**路由**（page 的职责），与"是否单页 / 列表"无关，因此不违背"不预设 Kind"。

占位符不再局限于 `{slug}`/`{publishTime:FORMAT}` 这两个名字——`name` 可以是 content 的任意字段，系统字段（如 `publishTime`）还是 `FlexFields` 业务字段一视同仁，对齐 Dignite.Cms 的 `EntryDtoExtensions.GetUrl`（反射取值，不硬编码字段名）。每个占位符现在有四种写法，都用 `:` 分隔：`{name}`、`{name:FORMAT}`、`{name:REGEX}`、`{name:FORMAT:REGEX}`——FORMAT 只影响**生成** URL 时怎么格式化这个值（`IFormattable.ToString(FORMAT)`），REGEX 只影响**解析**请求时接不接受捕获到的这段文本，二者互不干扰，可以只用一个也可以两个都用（例：`{publishTime:yyyy-MM:^\d{4}-(0[1-9]|1[0-2])$}`）。`name` 是否真的存在，`PageRoute` 管不了——它是 `Domain.Shared` 的静态类，够不着字段定义，这一层只校验语法。`name` 落不到 content 实际字段这件事，要等 `Page.BuildContentPath` 真正取值时才抛异常，不会把占位符原样吞进 URL、生成一条永远解析不了的坏链接。

只有一个 `:` 时，FORMAT 和 REGEX 写法上没有区别——都是"冒号后面一段文本"，靠内容判断：这段文本只要全部落在字母 / 数字 / `.` / `_` / `-` 这个字符集里，就判定是 FORMAT（这正是原来 FORMAT 字符集的定义，等于说所有已存在的 `{name:FORMAT}` 路由分类结果不变，零回归——一个真正的日期 FORMAT，比如 `yyyy-MM`，天然不可能落到这个字符集之外，哪怕它凑巧也是一个语法合法的正则）；不满足这个字符集的，就尝试当正则表达式编译，编译得过就是 REGEX，编译不过这个占位符就是非法路由。两个冒号（`{name:FORMAT:REGEX}`）不存在歧义，第一段按 FORMAT 字符集校验，第二段（哪怕自己还带冒号，比如时间正则 `^\d{2}:\d{2}$`）就是 REGEX。REGEX 段和 FORMAT 段一样禁止出现 `/`——哪怕正则本身对 `/` 没有特殊语义，也统一禁掉，理由和 FORMAT 一样：解析引擎靠字面量分隔符定位每个占位符的边界，一个占位符捕获到的文本只要含 `/`，就无从区分它是不是吃进了下一段路径。

解析不再委托给 ABP 自带的 `FormattedStringValueExtracter`（`Volo.Abp.Text.Formatting`）——它的分词器只按花括号切 token，一旦占位符自己的正则里出现花括号（比如量词 `\d{4}`，这是最普通的正则写法），第二个 `{` 出现时它会直接抛异常。`PageRoute` 现在自己做花括号深度感知的扫描来定位每个占位符真正的收尾括号（正则量词里配对的 `{4}`、`{2,4}` 会被正确跳过，反斜杠转义的 `\{`/`\}` 也不会打断计数），以及随后的字面量边界匹配（沿用 ABP 原算法的思路：靠 `IndexOf`/`StartsWith` 找字面文本，两段字面文本之间的内容归属前一个占位符）。这个引擎依然只做"整模板全量匹配"，不校验占位符捕获到的值符不符合它自己的 FORMAT（`:yyyy-MM` 只影响生成时怎么格式化，不影响解析时认不认）——REGEX 才是解析阶段唯一会校验捕获值的机制，且只在有 REGEX 时才校验：没有 REGEX 的占位符（不论是老的 `{name:FORMAT}` 还是新的裸 `{name}`）行为和以前完全一样，来者不拒。生成 URL 时 REGEX 部分整段丢弃——`Build` 只用得上 `name` 和 FORMAT，值解析链路（先查 content 的真实属性，查不到再查 FlexFields）不受影响。

`{slug}`/`{slug?}` 出现时**必须是 route 里最后一个占位符**。这条校验的意义要放到 §3.4 的部分匹配里才看得出来——它让"slug 之前的占位符"成为一段有明确边界、可以从深到浅切的前缀，而不是一堆没有固定顺序的集合。

### 3.4 路由解析流程

请求进来：**域名 → 租户/站点**（ABP Domain Tenant Resolver，见 §4）→ 用路径匹配 page 集合。核心规则是：**按路径从长到短试出"这段前缀属于哪个 page"；一旦某个长度上有 page 定了下来，不再退回去试更短的前缀**。同一长度上可能有不止一个 page 推导出同一个自身地址（两个 page 推导出同一个地址不是创建时的冲突，见下面的例子），这时候要在三层里依次找答案——不是字面量无条件优先于模板。

具体地：把归一化后的路径按段拆开，从整条路径本身开始，每次去掉最后一段，一直试到只剩根 `/`：

1. 在这个长度上，找出所有自身地址正好等于这段前缀的 page（按 §3.3 的推导规则算），记下这批候选一共有几个。
2. **第一层（结构化，占位符一个不少）**：这批候选先各自拿**完整的原始路径**（不是这段前缀本身）试结构化匹配——route 以 `{slug}`/`{slug?}` 收尾的，试完整填满全部占位符含 slug；不以 slug 收尾的，试填满它自己全部占位符，一个都不丢。谁先给出结构化答案谁就赢，不问它是字面量还是模板——字面量 route 没有占位符，天然给不出结构化答案，所以这一轮实际上只有模板 page 能赢。
3. **第二层（截断，只丢最后一个占位符）**：只有当这批候选**只有一个**、且它在第一层没有给出结构化答案时，才让它再试一次——把自己的占位符从后往前丢，丢到只剩 slug 之前那一段，看能不能凑上剩余路径（比如 `{publishTime}/{slug}` 丢掉 `{slug}`，单独试 `{publishTime}` 能不能凑）。**这批候选只要有两个或以上，这一层对谁都不跑**——一个更深的模板不能凭自己占位符多，就去猜一个可能已经有专门页面在管的地址，不管那个专门页面自己接不接得住这次请求。
4. **第三层（兜底，页面自身）**：还没定下来的候选，逐个当作"命中了这个 page 自己"，按字面量优先于模板的顺序试。一个模板候选如果自己的占位符解释不了剩余路径里多出来的部分（不管是第一层就形状不对，还是第二层被同址候选挡住、或者试了也没凑上），**不进这一层**——"就当是页面自身"会把请求里多出来的那部分悄悄吞掉，这正是三层设计要防的事。只有完全没有占位符的纯字面量路由，天生就没有别的机制去解释多出来的部分，才继续保留无条件进这一层的资格。
5. 第一个在这个长度上给出确定答案的 page（无论来自第 2、3、4 哪一层）就此定下来，**不再退回去试更短的前缀**——哪怕它接不住剩下的路径。

拿真实一点的例子说明为什么不能只按"最长的模板"或"整条路径"一次性判断，必须逐段试、且每段内部还要按三层分先后:route 是 `/blog/abc/{publishTime:yyyy-MM}/{slug}`（`abc` 是字面量，不是占位符）。请求 `/blog/abc/2026-08/my-post`：

- 整条路径（4 段）、去掉一段的 `/blog/abc/2026-08`（3 段）都不是任何 page 的自身地址；
- 再去掉一段，`/blog/abc`（2 段）——按 §3.3 的推导规则，这正是上面那个 page 自己的自身地址（它的第一个占位符在 `abc` 之后）。**如果另外单独建了一个字面量 `/blog/abc` page**，这一长度上就有两个候选：深层模板的占位符能把剩下的 `2026-08/my-post` 整段吃满（`publishTime=2026-08`、`slug=my-post`），字面量因为没有占位符必然吃不下——深层模板第一层胜出，如果 `my-post` 真查到已发布的内容，直接落到内容详情，字面量 page 根本轮不到出场。只有当 `my-post` 查无此内容时，深层模板才交不出结构化答案；这时因为字面量候选也在场（两个候选），第二层截断对深层模板不开放，直接进第三层兜底，字面量 page 赢——命中的是那个不相干的字面量 page，不是这条深层 route 的部分匹配。

再看只请求到 `/blog/abc/2026-08`（3 段，比详情少一段）会发生什么，这是第二层真正要解决的场景：
- 如果**没有**另建字面量 `/blog/abc` page，深层模板在 `/blog/abc` 这一长度上是唯一候选，第一层填不满全部占位符（凑不出 slug），但因为是唯一候选，第二层放行——丢掉 `{slug}`，单独试 `{publishTime}` 能不能凑上 `2026-08`，成功，返回这个 page 附带 `{"publishTime:yyyy-MM": "2026-08"}` 这样的筛选值，不查具体内容；
- 如果**另建了一个专门管这个地址、不带 slug 的 page**（比如 `/blog/abc/{publishTime:yyyy-MM}`，没有 `{slug}`，用来渲染"按月归档"这种独立视图），这一长度上就有两个候选——专门页面自己的占位符已经能一次填满（不用丢任何东西），第一层直接胜出，深层模板的第二层截断根本不会被尝试，筛选值来自专门页面而不是深层模板的猜测；
- 如果**另建的是一个纯字面量 `/blog/abc` page**（不带任何占位符），这一长度上还是两个候选——字面量对 3 段的请求既给不出第一层答案，又因为同址还有别的候选而没有第二层可试，深层模板同理（3 段比它自己完整长度少一段，第一层给不出答案，第二层因为同址候选被挡住）——两边都进不了第三层兜底（深层模板的占位符解释不了 `2026-08`，第三层明确把这种情况排除在外；字面量本身也解释不了多出来的这一段，不是"恰好是它自身地址"的情形）——这一长度上两个候选全部失败，整个长度作废，外层循环去试更短的前缀，最终大概率是 404，而不是像旧设计那样默默把这次请求当成深层模板的一次"按月筛选"来渲染。

page（连同它是哪一层赢的）确定下来之后，按赢的方式收尾：

- **第一层里，整条路径把这个 page 的全部占位符（含 slug）都填满** → 按 `(PageId, CultureName, Slug)` 取内容（§2.5 的唯一约束）——查到就是详情；查不到，这个候选在第一层的答案就是"没有下文"，把机会让给同一长度内的下一个候选，不会因为一个候选没查到内容就判定整个长度失败，也不会再给它第二、三层的机会；
- **第一层里，非 slug 的占位符全部填满**（比如上面"专门页面"那种情形）→ 返回这个 page，附带解出来的筛选值，不查任何具体内容；
- **第二层截断命中**（比如 `/blog/abc/2026-08` 落在唯一候选的深层 page 上）→ 返回这个 page，附带已经解出来的筛选值（`{"publishTime:yyyy-MM": "2026-08"}`），不查任何具体内容——前端可以用同一个 page 的模板渲染"按月筛选的列表"，不需要为这种筛选粒度单独建一个 page；
- **第三层兜底命中** → 查这个 page 下面 slug 为空的内容，查到是单页，查不到就是"page 本身，没有具体内容"，前端按列表渲染；
- 所有长度都没有 page 定下来 → 查重定向表 → 否则 404。

**根路径 `/` 只在请求本身就是 `/` 时才作为候选**，不会作为"任意深层路径一路剥到底"的兜底——首页几乎总是挂在 `/` 上，如果剥空也去试它，会让所有匹配不到的路径都意外落在首页上，而不是真正的 404。

这套"部分匹配"能力存在的直接原因：避免重蹈 Dignite.Cms 的覆辙——那边 `SectionType` 非 Single 的 Section 强制 Route 含 `{Slug}`，等于每建一个详情页都被逼着先想清楚列表怎么处理；Site 允许同一个 page 隐式身兼"列表、按某个占位符筛选的子列表、详情"三职，只有真需要一个用得上独立字段/模板的、专门的中间页面时，才额外建一个更具体的 page 顶到前面——第二层"唯一候选才截断"的限制正是为了让这个专门页面一旦真的建出来，就立刻接管，而不是继续被更深的模板猜中。

**渲染交前端**：后端解析出"命中了哪个 page / 哪条内容、它是什么 ContentType、有没有额外的筛选值"，前端决定渲染成单页、列表还是筛选后的列表，用哪套模板。后端不预设页面形态。

## 4. 站点配置（无 Site 实体）

早期设计里的 `Site` 聚合**已移除**。域名、语言、状态、主题、统计 ID、robots 策略等本质都是**设置项**，走 ABP 的能力即可，不必为它们立一个聚合。

### 4.1 走 ABP Settings（租户级）

语言、默认语言、主题、统计 ID、robots 策略、默认 OG 图、标题模板等 → **租户级 ABP Settings**。多租户隔离由 ABP 原生提供，A 租户的设置绝不串到 B。

### 4.2 域名：正向是设置，反向不在本仓库

域名这件事要拆成两半看，它们的答案不同：

- **正向**"当前租户的主域是什么" —— 这就是一个**租户级设置** `Site.PrimaryDomain`（绝对 origin，可带基础路径）。canonical、sitemap、robots、feed 的绝对 URL 全部据此生成，而**不是**据请求恰好落在哪个 host —— 后者正是多租户头号 SEO 坑：自定义域与平台子域都返回 200、各自自指，排名信号一分为二（见 §5）。留空时回退到当前请求的 scheme+host（仅 Web 层有此回退）。
- **反向**"给定 host 反查是哪个租户" —— 这是查找、不是设置，**已决定不在本仓库实现**（issue #12 关闭）：现成的 Domain-Names 模块（`Dignite.Abp.TenantDomainManagement`）只支持每租户一个自定义域且无反向索引，为它建索引意味着侵入另一个模块的存储或改其数据模型，当前不值得。平台子域解析（`{tenantName}.<平台域>`）则是部署方 Host 里 `AbpTenantResolveOptions.AddDomainTenantResolver(...)` 的一行配置，不是本模块的产品代码。

每站点一个主域名，副域名整站 301 到主域（重定向表见 §5.7）。

### 4.3 一租户一站点

- **一租户 = 一站点**。移除 Site 实体后此结论依然成立：租户就是站点，站点配置就是租户设置。
- **host 主站** = 无租户上下文（TenantId 为空）的那套设置，与租户站同构，无需特例代码。

## 5. 站点级派生能力（SEO / sitemap / 可发现性）

> 本章吸收自原《03-网站功能整合规划》，按 2026 现状核对，关键 footgun 已标。这些能力都是**从 Page 路由结构 + Content 存在性派生**、平台按"域名→租户"解析后自动产出的，**依赖路由、不依赖具体 SEO 字段值**——所以 SEO 字段下放到 ContentType（§5.3）不影响它们。

### 5.1 四条平台原则

普通建站工具让用户手填 SEO；Site 的每个功能都满足：
1. **每租户可配 + 平台有合理默认**——不配也开箱达标；
2. **模板 / 派生自动产出**——非技术用户零操作即获得（canonical、sitemap）；
3. **严格命名空间隔离**——租户间 sitemap / robots / 统计绝不串；
4. **AI 优先生成**——AI 既然已写内容，就顺手生成 meta、alt、hreflang、首段直答。

> 适用范围：以上"开箱达标"保证覆盖平台官方骨架（Tier 0，见 §7）。外部前端（Tier 1/2）需自行满足一致性清单。

### 5.2 sitemap（必备）

- 发布 / 变更时，从 **Page + Content** 生成：所有基础路由 page + 每个 page 下每条已发布内容展开的 URL。
- **[footgun] lastmod 只在内容真变时更新**——若全站都盖"今天"，Google 会**全站忽略**该字段。用内容的实际更新时间 / 内容哈希驱动。
- 单文件上限 5 万 URL / 50MB；实践按 **1–2 万 / 文件**分片 + gzip，按类型分片（pages / news / products）+ 每租户一个 sitemap index。
- 采用 **X.Web.Sitemap**（自动分片 + 索引），只写"从库里喂 URL + 分片键 + lastmod"这层胶水。

### 5.3 SEO（<head> 元数据 + 路由派生）

SEO 分成两半，各归其位：

**① 影响单页 `<head>` 的元数据 → ContentType 引入的字段。**
meta title / description、og:image、noindex 等，本就是"这条内容的元数据"，和正文一样，走普通字段机制、值存 Content、分语言。平台在**字段库里预置一组标准 SEO 字段**（§2.3 的 Field，租户开箱即有），带平台能识别的语义（例如 `noindex` 一旦有值，sitemap 就不收这条 URL）。ContentType 按需引入这组：引了就有平台级 SEO 能力（含 AI 自动填），不引走纯默认。

> **例外：新建 Page 自带的首个 ContentType。** 创建 Page 时平台顺带建一个同名 ContentType（否则这个 Page 无法创建任何 Content——Content 的归属全靠 ContentType 反向推出，见 §2.4），这个默认类型已经引入 SEO 字段组，管理员嫌多可以手动摘掉。此后再手动新增的 ContentType（同一 Page 下的第二、第三个类型，如 `post-gallery`）仍是纯按需勾选，不受此默认影响——"按需"仍是常规路径，这只是给了空 Page 一个更友好的起点。

> 字段库独立成表在这里正好兑现：SEO 字段组只定义一次，被多少个类型引入都是同一份定义——平台要识别 `noindex` 语义，认的是那个固定的 `FieldId`，不必在每个类型里按名字猜。

**② 从路由派生的产物 → 平台自动算。**
canonical（自指向主域绝对 URL）、hreflang、sitemap——平台从路由结构算，不读 SEO 字段。canonical 用 §4.2 的主域名生成；草稿 / 预览页强制 noindex。

标签输出复用 **`Dignite.Abp.Seo`（SeoTags）**，几乎零新代码。

### 5.4 结构化数据 JSON-LD（不做——交给前端）

**[决：曾经是后端必备核心类型，已移除，见 GitHub issue #20 后续讨论]**
- 后端不构建、不持久化任何 schema.org 映射（`ContentType.SchemaType`、`ContentTypeField.SchemaProperty` 均已删除），`HeadMetadataDto` 不再带 `JsonLdDocuments`/`MissingSchemaProperties`。理由见下。
- Site 的定位是 CMS：后端职责止于"正确、完整地把数据交出来"（Content 的字段值经 Public API 已可直接读到，§2.x）。JSON-LD 是不是要发、发哪种 schema.org 形状、字段怎么映射，属于渲染层决策——渲染层可以是平台自己的 Tier 0 骨架，也可以是租户自带的任意语言 Tier 1/2 前端（§7.1"前端不锁语言"），把这层决策收进后端等于替所有可能的前端做了一次选择，且需要每种前端各自重新实现 Schema.NET 等价的序列化正确性（转义、绝对 URL 校验、日期时区……）。
- 内容类型的字段定义（含每个字段的 `description`）本就走 Public API 可读，前端开发者或 AI 写前端时天然知道每个字段的语义，能直接调用，不需要平台再存一份 `schemaProperty` 映射。
- 以下 2025–2026 Google 富结果现状仍值得前端实现者参考，只是不再由平台强制：
  - 仍会产出富结果的类型：Organization / WebSite（全站级）、BreadcrumbList（路由可推导）、Article / NewsArticle / Product+Offer。
  - **[footgun] FAQPage / HowTo 富结果已下线**（FAQ 2026-05 停、HowTo 2023 起无）——仍可发供 AI 解析，但别指望 SERP 下拉。
  - **[变] Product 图**最小 500×500（2026-04 警告、2027-01 强制）。

### 5.5 多语言 hreflang（必备——多语言是核心设计）

- `hreflang` + `x-default` **由多语言分组自动生成**：按 §2.4 的自然键 `(PageId, ContentTypeId, Slug)` 聚合出同一内容的各语言行，取各行的 `CultureName` 直接作 `hreflang` 值（这正是它存 BCP 47 规范形式的原因之一），互指、自指、绝对 URL；`x-default` 指向中性首页。
- URL 策略默认**子目录 `/de/ /fr/`**（合并域名权重、最易自动化）；有法律 / 托管分离需求才用子域 / ccTLD。
- **默认语言不带前缀（已定）**：`Site.EnabledLanguages` 的**第一项**即默认语言，其 URL 无前缀，其余语言走 `/{culture}/`。不另设 `DefaultLanguage` 设置项 —— 两个设置会互相矛盾（不在启用列表里的默认语言没有定义），而排序已经能表达全部意图（想让法语不带前缀就写 `"fr,en"`）。
- **拼接与剥离必须同处一地（已定）**：`SiteUrlContext` 同时持有 `ApplyCulturePrefix` 与 `TryStripCulturePrefix`，与 `PageRoute`（§3.3）同理 —— 分散到两处必然漂移，结果是站点公布自己会 404 的 URL。剥离只在首段是**已启用且非默认**语言时发生，这样路由恰好叫 `/en` 的页面不会被误当成英文前缀。
- 我们"每语言一份记录 + 自然键分组"的模型，让 hreflang 几乎是免费副产品——一次 `GROUP BY` 就出，没有分组表要维护、也不会出现分组 Id 与数据脱节。
- **与子目录策略天然契合**：slug 跨语言一致（§2.4 的代价），各语言 URL 只差前缀（`/en/blog/my-trip` ↔ `/zh/blog/my-trip`），互指关系一眼可验。

### 5.6 robots + AI 爬虫开关（必备）

- `robots.txt` 每域名各自生成（按域名→租户解析）。
- **AI 爬虫开关**（当前唯一实用杠杆）：区分**训练类**（GPTBot / Google-Extended / ClaudeBot / CCBot）与**搜索/RAG 类**（OAI-SearchBot / PerplexityBot / Claude-SearchBot），每租户可分别开关。常见策略：放搜索、挡训练。
- `llms.txt` 低 ROI（约 10% 采用、Google 明确不支持），廉价自动生成、标为可选，不当排名手段。

### 5.7 重定向 / 错误 / TLS（必备）

每租户 `Redirect` 规则：301/302、改 slug 自动建 301、扁平化避免重定向链、品牌化**真 404**（避免 soft-404 返回 200 的模板陷阱）、HTTPS + 自定义域自动签证书（ACME / Let's Encrypt）+ HSTS。自建薄层（RewriteMiddleware + 每租户重定向表）。

### 5.8 性能 / Core Web Vitals（必备）

**[变：当前三指标 = LCP / INP / CLS；INP 2024-03 取代 FID]**，取 CrUX P75。
| 指标 | 良好阈值 | 备注 |
|---|---|---|
| LCP | ≤2.5s | |
| INP | ≤200ms | **2026 最常挂的指标**（约 43% 站点不达标） |
| CLS | ≤0.1 | 媒体 / 嵌入预留尺寸 |

支撑项（模板 / CDN 层）：AVIF/WebP + 响应式 srcset、below-fold lazy（LCP 图除外）、图片显式 width/height 防 CLS、LCP 图 fetchpriority=high、关键 CSS 内联、字体 font-display:swap、BLOB + CDN / 边缘做缩放与格式协商。

### 5.9 社交 / feed / 分析 / 无障碍

- **社交**：Open Graph（og:image 1200×630、<1MB、居中安全区）、Twitter summary_large_image、favicon 全套 + webmanifest。
- **feed**（博客近必备）：RSS / Atom 自动生成（`<link rel=alternate>` 自发现），数据源同为 Content。采用 `System.ServiceModel.Syndication` + `JsonFeed.NET`。
- **分析与隐私**：每租户统计 ID（GA4 / Plausible），Tag 容器隔离；GDPR Cookie 同意 + Google Consent Mode v2，同意前拦截非必要 tag。
- **无障碍**：WCAG 2.2 AA 基线（alt、label、对比度、焦点、跳转链接），AI 生成 alt 文本。搜索结果页 noindex。

## 6. AI / MCP 能力面

### 6.1 理念

平台把能力**开放为 MCP**，不内嵌后台助手。用户在自己的 AI 客户端里完成两类工作：
- **建站期**：口述创建 page（定路由）、在 page 下建 ContentType 并引入字段（字段库里没有就顺手新建 Field）、填充 Content（填内容），甚至构建前端模板。
- **运维期**：口述发布 / 修改内容（"发一条新闻，正文如下……"），AI 客户端调 MCP 工具，平台按字段定义校验、入库，路由与 sitemap 自动更新。

`schema 即契约`在这里兑现：ContentType 引入的那组 Field 就是 AI 生成内容的目标形状，也是写入校验闸门；AI 顺手产出的 SEO 字段（meta / alt / 首段直答）同样过闸门。

### 6.2 工具面（已定）

**结论：按实体切，用名字寻址，schema 由一个只读工具整体交付。**不按场景切；不给每个租户动态生成工具。（GitHub issue #25）

#### 6.2.1 切法：为什么不是按场景

三个候选按三条标准量一遍——"发一条新闻"要几个来回、能不能直接落到 ABP 权限、平台要猜多少：

| 切法 | "发一条新闻"要几个来回 | 落 ABP 权限 | 平台要猜什么 |
|---|---|---|---|
| 按实体（即现在 AppService 的形状，Guid 寻址） | **4**：查 page → 查 ContentType → 查 Field 定义 → 建 Content | 1:1，零成本 | 不猜 |
| **按实体 + 名字寻址 + 一个 schema 工具**（本节结论） | **2**：取 schema → 建 Content（schema 走 MCP resource 时为 1） | 1:1，零成本 | 不猜 |
| 按场景（`publish_article`） | 1 | 要另建一张映射表 | 落哪个 page、哪个 ContentType、正文是哪个字段、发布还是草稿 |
| 每租户动态生成工具 | 1 | 1:1（生成的工具继承其实体的权限） | 不猜，但工具清单随 schema 变动、条数随 ContentType 线性增长 |

那 4 个来回里有 3 个是**发现**、只有 1 个是写入；而且第三步无法省略——`ContentTypeField` 只带 `FieldId` 与用法开关，字段的 `Name`（也就是值袋的 key）在另一张表上。所以缩短来回的办法**不是把工具做粗，是把 schema 一次交付**。

按场景切的真正问题不在来回数，在于它要平台替租户猜。`/blog` 下同时有 `post-article` / `post-gallery` / `post-video`（§2.6）时，`publish_article` 只能靠工具名猜命中哪个——可这三个名字是**租户的运行时数据**，一个编译期定死的工具名不可能知道。这与 §1.2 理念 ③ 正面冲突：契约是**租户的** schema，不是平台在其上另发明的一套动词。

动态生成工具（把每个 ContentType 编译成一个 `create_news_item`）能把来回压到 1，且工具的 JSON Schema 字面上就是那个 ContentType 的字段编排——理念上最纯。不采用的理由是运营面：工具清单会随租户改一次 ContentType 而变（依赖客户端对 `tools/list_changed` 的支持程度）、条数随类型数增长挤占客户端上下文。**留作后路**：若 2 个来回被证明是真瓶颈，这是下一步，而不是改成按场景。

#### 6.2.2 一条准则

> **工具可以编排多次 manager 调用，但工具不能替 manager 做决定。**
> 一旦某个工具需要推断"落哪个 page / 哪个 ContentType / 这个值是哪个字段"，它就是在猜，答案应该出现在交给客户端的 schema 里，而不是写进工具实现。

这条准则是 MCP 作为**第二条写入路径**的护栏。ContentManager 持 slug 唯一性、culture 规范化、page/type 自洽与字段校验；FieldManager 持改名次序（`Field.Name` 是值袋的 key，改名是数据迁移，§2.4）。**工具是另一个调用方，不是另一份实现**——重复校验就是从这里长出来的。

#### 6.2.3 工具清单

按实体切，读写各就其位。约 18 个静态工具，条数与租户规模无关。

| 工具 | 打给 | ABP 权限 | MCP 注解 |
|---|---|---|---|
| `get_site_schema` | 新增 `ISiteSchemaAdminAppService`（见 6.2.4） | `Admin.Pages` + `Admin.ContentTypes` + `Admin.Fields` | readOnly |
| `list_contents` / `get_content` | `IContentAdminAppService` | `Admin.Contents` | readOnly |
| `list_fields` | `IFieldAdminAppService.GetListAsync` | `Admin.Fields` | readOnly |
| `resolve_path` | `IRoutingPublicAppService.ResolveAsync` | 无（Public 面） | readOnly |
| `create_content` | `IContentAdminAppService.CreateAsync` | `Admin.Contents.Create` | — |
| `update_content` | 同上 `UpdateAsync` | `Admin.Contents.Update` | idempotent |
| `delete_content` | 同上 `DeleteAsync` | `Admin.Contents.Delete` | **destructive** |
| `create_page` / `update_page` / `delete_page` | `IPageAdminAppService` | `Admin.Pages.{Create,Update,Delete}` | delete 为 **destructive** |
| `create_content_type` / `update_content_type` / `delete_content_type` | `IContentTypeAdminAppService` | `Admin.ContentTypes.{Create,Update,Delete}` | delete 为 **destructive** |
| `create_field` / `update_field` / `delete_field` | `IFieldAdminAppService` | `Admin.Fields.{Create,Update,Delete}` | delete 为 **destructive** |
| `rename_field` | `IFieldAdminAppService.RenameAsync` | `Admin.Fields.Rename` | **destructive** |

- **`get_site_schema` 要三条权限，不是两条。**它把字段定义整个合并进来（含 `configuration`），而字段库由 `Admin.Fields` 独立把守；只要 `Pages` + `ContentTypes`，一个被显式拒掉 `Admin.Fields` 的角色就能从 schema 里读到 `list_fields` 不给它的东西。代价要认清：**给 MCP 用的角色若不授 `Admin.Fields`，`get_site_schema` 会直接从 `tools/list` 里消失**——而它是入口工具，没有它其余按名寻址的工具都无从下手。
- **`Fields.Rename` 与 `Fields.Update` 本来就是两条权限**，正因为改名是一次跨全表的数据迁移。这个粒度按实体切是白拿的；按场景切要重新推导一遍——这是"实体切法与既有权限同构"最直接的证据。
- **不做 FieldGroup 的工具**。字段分组"纯管理用途、不影响运行时"（§2.3），在 AI 客户端的工具清单里是纯噪音。
- **`delete_page` 级联删掉其下全部 ContentType 与 Content**（§2.5，库级 cascade）。它是这张表里唯一"一次调用抹掉一个栏目"的工具，因此默认给 MCP 用的角色**不授** `Admin.Pages.Delete`。

**唯一允许的复合工具**：`create_page_with_types`——一次调用建 page + 其下 ContentType（+ 顺手建缺的 Field）。它通过 6.2.2 的准则（结构由用户口述给出，工具不推断任何东西），解决的是建站期真实存在的次序与原子性问题（Field 必须先于引用它的 ContentType 存在；建到一半失败会留下半个站点）。条件三条：**单个 UoW**、**权限取并集**（`Pages.Create` ∧ `ContentTypes.Create` ∧ `Fields.Create`）、**零推断**。P2 之内可后置。

#### 6.2.4 schema 怎么交付

`get_site_schema` 一次返回 AI 生成内容所需的全部目标形状——这是 §1.2 理念 ③ 的兑现点：

- **站点**：启用语言（有序，首项即默认、URL 无前缀，§5.5）、主域名；
- **每个 page**：`name` / `route` / `contentPathPattern` / `isHomePage`；
- **每个 ContentType**：`name` / `displayName` / `description` / `schemaType`；
- **每个字段**：`name` / `displayName` / `description` / `fieldTypeName` / `configuration` + 本类型内的 `required` / `searchable` / `order`。

**复用既有的三源合并，不另写一份**。`IFlexFieldProvider<Content>`（`ContentFlexFieldProvider`）已经在做"定义 ∪ 用法 ∪ 值"的合并，schema 要的正是前两源。把"定义 ∪ 用法"抽成一个 domain 侧 resolver，provider 与 schema 服务共用即可——**这是本设计需要新增的唯一领域代码**，且是只读的，不构成第二条写入路径。应用层的新增只有两处：这个 schema 服务，以及 page / ContentType 按 `Name` 查的读方法（仓储上 `FindByNameAsync` 已存在，AppService 上还没暴露）。

**名字寻址，不传 Guid**。`Page.Name` 租户内唯一、`ContentType.Name` page 内唯一、`Field.Name` 租户内唯一且本就是值袋的 key——三层全都有天然的字符串主键，客户端不需要搬运任何 Guid。Guid 对 LLM 是纯成本：占 token，且是幻觉的高发面。名字→Guid 的解析走 AppService 读方法（因此仍过 `[Authorize]` 闸门），不绕到仓储。

同一份 schema 同时挂成 MCP **resource**（`site://schema`），支持 resource 的客户端连上就有，"发一条新闻"降到 1 次工具调用；不支持的走 `get_site_schema`。

**工具 JSON Schema 的三个坑（都是给模型准备的，不是给人）**：

- **`slug` 必填**（允许显式空串）。空 slug 是"页面唯一内容"的合法值（§2.4），而 `CreateContentDto.Slug` 默认就是空串——对人手写的 HTTP 请求无所谓，对模型不是：漏字段是模型最常见的失败，而这里漏掉不报"缺参数"，会静默抢占页面自身的 URL（§8.3 注已记过这个坑）或撞唯一约束。必填 = 逼模型把意图说出来。此外**工具层还负责把 slug 规范化**（`McpSlug`）：模型交上来的常是标题而非 slug，`"My Trip!"` → `my-trip`；走 `SlugNormalizer.TryNormalize` 而非 `Normalize`，因为纯标点的输入会规范化成空串，而空串在这里是另一个意思，只能报错不能吞。这一步是工具层自己加的，`ContentManager` 仍按原样存——对已经产出合法 slug 的调用方（后台 API、seed）那是对的，口述路径才是"原始标题进来"的那条。
- **`cultureName` 不在工具层规范化**，原样透传给 ContentManager。第二个规范化点正是 §2.4 警告的那种漂移。要让模型别自己发明 `zh-CN` 还是 `zh-Hans`，靠的是把租户已启用语言摆在它眼前——**落地时确认：静态工具的 JSON Schema 是编译期固定的，装不下每租户的枚举**，所以这件事由 `get_site_schema` 的 `enabledLanguages` 承担，工具参数的 description 指向它。（读路径是另一回事：按 page + 语言 + slug 找内容时，地址必须先规范化成已存的形式，否则客户端写 `zh-hans` 之后就读不回来——这一步落在 `ContentAdminAppService.FindBySlugAsync`，用的是同一个 `CultureNameNormalizer`，不是第二套规则。）
- **错误结构化回传，不 stringify**。`AbpValidationException` 的 `ValidationResult.MemberNames` 就是字段名，原样带上，客户端一个回合即可自纠；`ContentSlugAlreadyExistException` 一类带错误码。把这些压成一句人话，等于把闸门的诊断信息丢掉。

SEO 字段（§5.3 的 `seo` 预设）落在这里是**免费**的：它一旦被 ContentType 引入，就出现在上面那份 schema 里、带着自己的 description，AI 写正文时顺手填是最自然的动作，而不是另一个步骤——这正是 issue #27 要的机制，不需要额外的工具。

#### 6.2.5 权限与令牌

**不发明 MCP 专属权限。**工具打给 AppService，AppService 上的 `[Authorize]` 与传输无关，照常生效。读写分离**不是第三种切法**，是每个工具的属性，且代码里早已分好（Admin 与 Public 两套 AppService，`PublicPermissions` 至今为空）。兑现在两处：

1. **`tools/list` 按 ABP 权限过滤**——当前用户没有的权限对应的工具根本不出现在清单里。这不只是安全，更是省回合：模型不会把回合浪费在必然 403 的调用上。
2. **每个工具声明 MCP 注解**（`readOnlyHint` / `destructiveHint` / `idempotentHint`），客户端据此决定要不要弹确认。

只读客户端 = 只授 `.Default` 那几条权限的角色，**不需要第二套工具**。MCP 面向创作，所以工具打给 Admin 一侧（看得见草稿）；Public 一侧只出已发布内容，把它开成**匿名** MCP 端点是另一个决定（且与 §5.6 的 AI 爬虫开关耦合），P2 不做。

**令牌：与 HTTP API 同一套。**同一个 OpenIddict 授权服务器、同一套 scope 与权限声明，不另发 API key。理由与"工具是另一个调用方"是同一句话：ABP 的权限检查读 `ICurrentUser`、租户从 token 的 `tenantid` claim 解析，复用 token 等于这两件事零新代码。

MCP 客户端不是持预发 key 的服务，它走 OAuth 流：受保护资源要发布 `/.well-known/oauth-protected-resource`（RFC 9728）指向授权服务器。"同一套令牌"指的是同一个授权服务器与同一套权限声明，**不等于**开箱即通——这一层在 #26 里补上（见 6.2.7）。无人值守场景（CI 里发稿）用 `client_credentials` + 一个专属 OpenIddict application，仍在同一套体系内，不新增机制。

#### 6.2.6 代价要认

1. **首帖比按场景切多一个来回**。走 resource 时可抹平，但不能保证所有客户端都支持。
2. **"新闻" → `news-item` 的映射推给了模型**。这是刻意的（模型更擅长，且改起来不用动平台），但它意味着效果取决于租户把 `Description` 写好。因此 `ContentType.Description` 与 `Field.Description` 不再是"可选说明"，而是**面向 AI 的产品文案**——后台表单要把它摆在显眼位置，平台预置项要自带范文。
3. **约 18 个工具常驻客户端上下文**。常数、不随租户增长，但不免费。
4. **不做匿名 / 公开的 MCP 读端点**（见 6.2.5）。
5. **不为批量设计**。一次导入 200 条仍是 200 次调用；那是 HTTP API 的活，不是口述路径的场景。

#### 6.2.7 落地结论（issue #26）

工具面按 6.2.1–6.2.6 实现完毕，落地过程中确认与修正的几点：

- **端点与传输**：`/mcp`，Streamable HTTP，`Stateless = true`（`2026-07-28` 协议修订起是 SDK 默认）。选它不只是为了负载均衡——**每个 MCP 请求就此变成一次普通 HTTP 请求，走宿主原本那条管线**：OpenIddict 验完 bearer、ABP 从 `tenantid` claim 解析租户并开好 UoW，全都发生在端点执行之前。所以"认证 + 多租户 + UoW"这三件事的新增代码是零，而这是传输选择的结果，不是运气。
- **端点挂载**走 `AbpEndpointRouterOptions.EndpointConfigureActions`，模块因此不拥有任何中间件次序。
- **`tools/list` 权限过滤**由 SDK 的 `AddAuthorizationFilters()` 承担，识别工具与 resource 上的 `[Authorize]`；ABP 的 `AbpAuthorizationPolicyProvider` 把权限名当 policy 解析，所以 `[Authorize(AdminPermissions.Contents.Create)]` 直接可用。它同时管清单过滤与调用拦截。
- **认证方案必须显式指定**。ABP MVC 宿主的默认挑战方案是 Identity 的 cookie，未认证的 MCP 请求会被答成 `302` 跳登录页——那是 MCP 客户端无法处理的东西。端点要钉在 MCP 方案上（它把认证转发给 OpenIddict，挑战时回 `401` + `WWW-Authenticate: Bearer resource_metadata="…"`）。另外 SDK 的 `ForwardAuthenticate` 默认指向一个名为 `"Bearer"` 的方案（其 JwtBearer 示例注册的那个），本仓库没有，必须改指 OpenIddict 的验证方案。
- **注册机制：预注册客户端**（`Site_Mcp` 公共客户端 + PKCE，`Site_Mcp_Service` 走 `client_credentials`）。这不是 DCR 的替代品——预注册本就是 MCP 规范给客户端排的**第一优先级**（顺序：预注册 → CIMD → DCR → 提示用户手填）。**DCR 在 `2026-07-28` 修订中已正式废弃、后续版本会移除**，故不做；其继任者 CIMD 是授权服务器侧能力（AS 元数据出 `client_id_metadata_document_supported`、按 URL 形式的 `client_id` 拉客户端元数据文档），要落也在 OpenIddict 那边，不属于本仓库。
- **`Site_Mcp_Service` 不预授任何权限**。client_credentials 令牌不带用户，ABP 转而按客户端授权解析权限；默认全空意味着它开箱即用地什么都调不动，由部署方按需授（provider `"C"`，key 为 client id）。给一个密钥是公开默认值的客户端预授 `Admin.*` 是不能接受的。
- **领域侧唯一新增**：`ContentTypeFieldResolver`（"定义 ∪ 用法"），`ContentFlexFieldProvider` 与 schema 服务共用，只读。应用层新增 `ISiteSchemaAdminAppService` 与四个按名读方法（page / ContentType / Field 的 `FindByNameAsync`，Content 的 `FindBySlugAsync`），与 6.2.4 的预计一致。
- **工具比 6.2.3 的表多一个**：`list_field_types`（打给早已存在的 `IFieldAdminAppService.GetFieldTypesAsync`）。`create_field` 要求一个合法的 `fieldTypeName`，而那份清单是运行时注册的，模型没处猜；共 19 个。
- **未做**：`create_page_with_types` 复合工具（6.2.3 允许、且"P2 之内可后置"），另开 issue。

## 7. 前端架构（混合无头）

> 本章吸收自原《06-开放式前端架构》。方向：前端不锁定语言 / 框架，官方提供配套骨架，开发者也可贡献前端。与内容内核（§2）正交——内核不因前端选择而改。**部分细节仍是探索方向，待拍板项见 §10。**

### 7.1 混合无头

官方骨架与任意技术栈的外部前端并存，共享同一套内容内核（先例：Shopify 的 Liquid 托管主题 + Storefront API 外部前端并行多年）。设计收在两条原则上：渲染引擎只新增 **Scriban** 一个变量；契约克制（后端只暴露一小撮稳定通用的原语）。

### 7.2 Razor 归 ASP.NET Core，Scriban 是唯一新增

- 需要 Razor 时，**直接用 ASP.NET Core 原生的 MVC View / Razor Page / Blazor**——编译期检查、IntelliSense、调试、TagHelper 一样不少，不必借 ABP TextTemplating 包一层。
- **Scriban 存在的唯一理由是安全**：它是唯一可以放心交给租户 / AI 直接写、不担心执行任意代码的引擎。

| | 谁写 | 用什么渲染 | 能否被租户/AI 改 |
|---|---|---|---|
| 平台固定页面 / 组件 | 开发者 | ASP.NET Core 原生 Razor | 否——编译产物，走发布流程 |
| 租户 / AI 内容槽 | 租户或 AI | **Scriban**（沙箱） | 是——数据，不经编译，覆盖即生效 |

### 7.3 三层前端

| 层级 | 例子 | 与内核的关系 | SEO / SSR 责任 |
|---|---|---|---|
| **Tier 0 同进程动态骨架**（推荐 ASP.NET Core MVC） | MVC catch-all + Scriban 内嵌 | 直接调 Application Service，无 HTTP 往返 | 平台保证（§5 四原则在此兑现） |
| **Tier 1 跨进程动态骨架** | Next.js、Astro、独立 ASP.NET | 经 Delivery API（只读、只出已发布、版本化）读写 | 前端自负，平台给一致性清单 |
| **Tier 2 纯静态资源托管** | 用户上传的静态 HTML/CSS/JS | 不涉及内核，走 BLOB 托管 | 前端自负，平台不介入 |

MVC 的 `MapControllerRoute` `{*path}` catch-all 能对接运行时可变的路由（路由集合是数据，不是编译期常量），是 Tier 0 的自然选择。

### 7.4 动态路由表 = Page / Content 索引 + resolve-path 契约

"服务器端动态路由表"不是新组件——就是 §2 的 Page / Content 表。真正新增的只是一个契约动作：`resolve-path(path) → { matched, template, engine }`。Tier 0 里是进程内查询；Tier 1 里是 Delivery API 的一个端点——同一张表，两种触达。

### 7.5 安全边界

**凡"Razor"一律平台 / 开发者专属、走编译管线；凡需租户 / AI 写，一律落 Scriban，没有第二条路。** 允许租户内容进编译管线 = 允许其执行任意 C#，是远程代码执行，不是渲染。

Scriban 沙箱要点：`MemberFilter` 白名单只暴露公共属性，阻断方法调用与反射逃逸；默认无模板加载器（`include` 读不到文件系统）；循环上限 1000、递归上限 100；只暴露传入模型、全局字典与本地化助手。

## 8. 技术选型（Build vs Adopt）

> 本章吸收自原《04-技术选型》。**原则**：优先复用成熟、维护良好、许可证兼容的开源库；能复用 Dignite 自有模块最优先；只有现成轮子不合适、或与多租户 / AI 核心诉求冲突才自建，且自建尽量做薄。每引入依赖检查三件事：许可证兼容、近一年有维护、非单点维护。

### 8.1 决策顺序

先看 Dignite.* 自有 → 再看 ABP / 生态 → 再看通用 .NET 开源库 → 都不合适才自建（薄胶水层）。

### 8.2 复用 Dignite 生态（最大杠杆）

| 自有模块 | 能力 | 对 Site 的意义 |
|---|---|---|
| **Dignite.Abp.FlexFields** | 字段类型抽象（`IFieldType` × 6 内置 + DI 扩展）、值袋（`IHasFlexFields`）、派生索引与查询下推、校验、改名迁移 | **整个字段体系的底座**。Site 只出 `Field : IFlexField`、`Content : IHasFlexFields`、`IFlexFieldProvider<Content>` 和一张索引表，机制全由内核给 |
| **Dignite.Abp.Seo** | SeoTags（meta/OG/Twitter/canonical） | SEO 标签直接复用，几乎零新代码 |
| **Dignite.Cms** | 无头、可定义字段、多租户 / 多站点 / 多语言 / 版本化 | 内容内核的 DNA 来源（Site 是其下一代） |
| **dignite-abp 单仓** | File Management（BlobStoring）、Themes、多租户 Localization、Domain-Names、Regionalization | 媒体、主题、多语言全是现成件。**Domain-Names 例外**：它只存"每租户一个自定义域"的设置、无反向索引，撑不起 host→tenant 查找，故该能力已移出本仓库范围（§4.2） |

### 8.3 采用的库

| 能力 | 库 | 许可证 |
|---|---|---|
| 字段体系（类型 / 值袋 / 索引 / 校验） | Dignite.Abp.FlexFields（`.Domain` + `.EntityFrameworkCore`） | LGPL-3.0-only |
| Meta/OG/Twitter | Dignite.Abp.Seo（SeoTags） | MIT |
| XML sitemap + 索引 | X.Web.Sitemap | MIT |
| RSS / Atom | System.ServiceModel.Syndication | MIT |
| JSON Feed | JsonFeed.NET | MIT |
| 富文本渲染（markdown 模式时） | Markdig | BSD-2 |
| HTML 净化 | HtmlSanitizer（Ganss.Xss） | MIT |
| 图片处理（需 AVIF） | Magick.NET | Apache-2.0 |
| slug 规范化 | Slugify.Core | MIT |
| 模板引擎（租户 / AI 可写） | Scriban | BSD-2 |

> 注：内容改回数据库存储后，早期为"md + frontmatter"选的 YamlDotNet / frontmatter 解析**不再需要**。

> **slug 不做音译（已定）**。早期表格里的"中文→拼音（ToolGood.Words.Pinyin）"**已移除**：Site 是面向国际的开源项目，中文用户反而是少数，任何一张音译表都是**某一种语言的策略**——内置拼音就等于抬高中文、而其它语种继续退化成空串。`SlugNormalizer` 改为**保留 Unicode 字母与数字**（`我的旅行`、`Мой отпуск`、`日本語のタイトル` 均直接可用），percent-encoded UTF-8 路径本来就是合法且可索引的 URL。需要罗马化的部署自己先音译再传入——而且主路径上 slug 本就由调用方（MCP 客户端 / 编辑）给出，不是从标题推导的。
>
> 两个已在测试里钉死的坑：Slugify **默认 deny-list 是纯 ASCII**（非拉丁文一律出空串或 `-`，而空 slug 在本模型里是"页面唯一内容"的合法值，会静默抢占页面自身 URL）；输出必须**重新规范化为 NFC**（Slugify 内部走 NFD 折叠拉丁变音符，谚文分解出的是字母而非组合符，不会被还原——渲染一样但码点不同，浏览器发来的 NFC 永远匹配不上，唯一约束也会把两者当成两条内容）。

### 8.4 许可证红线（开源项目硬约束）

- **避开 `Imageflow`**（运行时实际 AGPLv3）、**`Unidecode.NET`**（转写数据表源自 GPL-2.0，有传染风险）。注：Site 现已完全不做音译，见 §8.3 注，故此条对 slug 而言已无实际约束对象。
- **`SixLabors.ImageSharp`** 双轨许可，开源项目适用 Apache-2.0 但需 README 披露；要 AVIF 直接用 **Magick.NET** 更省心。
- **可放心消费 LGPL**：ABP 核心、Dignite 模块均 LGPL-3.0，仅"修改它们本身"才需回馈。
- 其余推荐项 MIT / BSD-2 / Apache-2.0 / ISC，无商业触发。

### 8.5 自建的薄层

只保留四处自建，都是薄层或差异化价值：**robots 端点**、**重定向表**、**hreflang 装配**（复用 SeoTags 的 alternate）、以及**把上述库编排进一个租户感知的薄模块**。加一处前端的 **Cookie 同意**（ASP.NET Core cookie-policy 中间件 + JS CMP）。**MCP 能力面 + AI 生成胶水**是核心差异化，必自建。

## 10. 开放问题（待拍板）

1. ~~**富文本格式**~~（**已定**）：**由客户端编辑器组件决定，不在 Site 这一层拍板**。计划做 `Dignite.Abp.FlexFields.Ckeditor` —— 一个 FlexFields 的**外挂字段类型**（与 `.FileExplorer` 同形态：小项目 + 自注册，不改内核），基于 CKEditor，**在字段的 `Configuration` 里设 html 模式还是 markdown 模式**。
   - 由此 Markdig 只在 markdown 模式下才需要，HtmlSanitizer 则在 html 模式下必备。
   - 该字段类型的 `IndexValueType` 应为 `null`（富文本不可索引），与内核对 RichText 的既定假设一致。
   - 落在 flex-fields 仓库还是 Site 仓库待定；按"字段类型是通用能力、不绑 CMS"的分层，倾向前者。
2. ~~**MCP 工具面**~~（**已定**，见 §6.2）：**按实体切 + 名字寻址 + 一个 schema 工具**；读写分离不是第三种切法，而是"`tools/list` 按权限过滤 + 每工具声明 MCP 注解"两件事；权限直接复用 `AdminPermissions`，不发明 MCP 专属权限；令牌与 HTTP API 同一套 OpenIddict 授权服务器。
3. **前端 Scriban 集成**：借道 ABP TextTemplating（`.WithScribanEngine()`）还是裸接 Scriban 包？`ScribanViewResult` 走自定义 `IActionResult`？（原 06 §11 的待拍板项）
4. **渲染引擎标记**：Page 上做成显式字段，还是按内容来源隐式推导？
5. **单例约束**：是否需要"某 page 最多一条内容"的软约束（防"关于我们"被误加第二条）——开发时再定。

# Dignite Sites — 总体设计

> 本文是 Dignite Sites 的**权威设计文档**，取代早期分散的 6 篇讨论稿（架构对标 / 领域模型 / SEO 规划 / 技术选型 / 演进策略 / 开放式前端）。定位、概念模型、站点能力、前端与选型均以本文为准。
>
> 当前处于**设计沟通阶段，尚未编码**。用 Abp Studio 全新创建解决方案后再讨论具体实施。

## 1. 定位与核心理念

### 1.1 是什么

Dignite Sites 是**多租户站群平台**，是 **Dignite.Cms 的 AI 原生下一代**，跑在 ABP 之上。它保留 Cms 已验证的 DNA——字段定义、多租户、多语言、版本化——把内容的**录入接口从"后台表单"换成"用户自己 AI 客户端里的 MCP"**，并补齐 Cms 缺失的站点层（SEO / sitemap / feed / 域名）。

产品名 `Sites`（复数）= 平台层面 N 个租户 × 每租户 1 个站点；单数概念上的"站点" = 每个租户对应的那一个站点。

### 1.2 三个核心理念

**① 一切皆 page，page 即路由。**
页面的第一职责是路由。即使外部前端自带路由，后端的 page 集合仍然是**权威路由表**——因为 sitemap、canonical、hreflang 这些站点级产物全部从它派生。这是 page 存在的根本理由。

**② AI 通过 MCP，平台不做后台助手。**
平台**不内嵌** AI 助手。差异化在于把平台能力开放为 **MCP**，智能在用户自己的 AI 客户端里：用户口述"建一个页面，路由是 xx，内容是 xx"或"发一条新闻（粘贴正文）"，AI 客户端调 MCP 工具，平台按字段定义校验、入库，路由与 sitemap 自动更新。建站期与运维期都是这一条路径。

**③ schema 即契约。**
字段定义既是内容写入的**校验闸门**，也是喂给 AI 的**目标形状**。这是从早期 flat-file 调研里保留下来的最有价值的一条理念——尽管内容存储最终定回了数据库，这条理念独立成立。

### 1.3 与传统 CMS 的差异

传统 CMS 让用户在后台手填表单。Sites 把这套能力开放成 MCP，用户在客户端口述完成建站与日常运维。**原有架构（字段定义、条目、版本化、多租户）全部保留**，变的只是"谁来写、怎么写"。

MCP 优先不排斥将来平台自己再内嵌助手，两者不冲突；但那不是当前目标。

### 1.4 存储决策（已定）

内容以**数据库**为事实来源，沿用 Dignite.Cms 已验证的"字段定义 + 条目 + 版本化"内核。

> 早期文档提出的"文件（md + frontmatter）为唯一事实来源、EF 只存可再生索引"方案**已废弃**。理由：一旦主流程变成 MCP 直写，flat-file 的最大卖点（Git 分支 / PR 人审 / 天然版本化 / 可移植）大幅缩水，而其代价（每租户可写存储、索引重建、并发写入）一个不少。Git / PR / 版本化 / 可移植是**前端模板与代码**层面的事，与内容层无关。

### 1.5 适用边界

展示型 / 内容型站点——新闻、页面、博客、产品展示，这是本方案的主场。一旦进入事务 / 交互逻辑（购物车、库存、订单），另上后端 + 关系库，不硬套。CMS 本就服务于展示层，这条边界要守住。

### 1.6 命名（已定）

项目定名 **`Dignite.Sites`**，包名线 `Dignite.Sites.*`（Domain / Application / Application.Contracts / EntityFrameworkCore / HttpApi / Web）。

- **不叫（回）Cms**："Management System" 自带"后台"心智，正是本项目背离的方向（后台表单 → MCP 口述）；且需与上一代 `Dignite.Cms`（进维护模式）清晰区隔——换名才说得清"这是换代不是升级"。
- **选 Sites**：成果导向（用户做出的是一个个网站）、贴合多租户站群本质（复数）、sitemap / 域名 / SEO 本就是 site 层面能力；"泛"由 `Dignite.` 前缀消解。（曾认真考虑 `Pages`——扣"一切皆 page"理念——但它在 web 圈已被 GitHub/Cloudflare Pages 占成"静态托管"心智，弃。）
- **AI 不进包名**：AI 是当前最强手段而非产品的持久本质（避免像 "Cloud xxx" 那样过时）。AI 原生放在副标题 / 仓库描述：*AI-native, MCP-first multi-tenant site platform for ABP*。

## 2. 概念模型（核心）

### 2.1 三个核心实体

整个模型收敛为三个核心实体，正好对应"page / 字段 / 内容"，再加一张**独立的字段定义表**作为支撑，**整套结构对齐 Dignite.Cms 已验证的成熟模型**：

| Sites | ≈ Dignite.Cms / Craft | 是什么 | 一句话职责 |
|---|---|---|---|
| **Page** | Section | 路由节点 | 这个 URL 存在、下面有哪些内容类型、用什么模板 |
| **ContentType** | EntryType | 内容类型 | **隶属于某个 Page**，编排一组字段，定义"这种内容长什么样" |
| **Content** | Entry | 内容记录 | 按某个内容类型、落在某个路由下的一条数据 |
| **Field** | Field | 字段定义（独立表） | **租户级字段库**，一次定义、被多个 ContentType 复用 |

**三层归属链**：`Page → ContentType → Field`（引用），内容落在 `Content(PageId, ContentTypeId, 各字段值)`。ContentType 隶属 Page、不跨 page 共享；**复用发生在字段层**——同一个 Field 可被任意多个 ContentType 引入。

配置（域名、语言等）**不是实体**，见 §4；站点级能力（sitemap 等）是**派生产物**，见 §5。

### 2.2 Page（路由节点）

| 属性 | 说明 |
|---|---|
| **Route** | 核心属性。基础路径，如 `/about`、`/blog`、`/news` |
| **下辖的 ContentType** | **一对多隶属**：ContentType 建在 page 之下（外键 `PageId`），一个 page 可以承载多种形态的内容（见 §2.6 例子） |
| **内容路径模式** | 可选。决定该 page 下内容的 URL 怎么拼，默认 `{slug}`；要日期段就 `{date:yyyy/MM}/{slug}`（对齐 Dignite.Cms） |
| **Template** | 可选。渲染模板引用。仅在需要后端点名视图的前端模式（MVC catch-all）下用；Razor Pages / 外部前端自带渲染则用不到（见 §7） |
| 导航相关 | IsHomePage、Order（导航排序）、Status——聊导航时再细化 |

Page **不预设 Kind**（单页 / 列表 / 详情不区分）、**不含字段定义**、**不挂 SEO**。它就是纯路由 + 下辖的类型 + 渲染提示。

### 2.3 ContentType（内容类型）与 Field（字段库）

字段定义**不内联在 ContentType 里**，而是独立成表。这是与 Dignite.Cms 一致的做法，两者职责分开：

- **Field = 字段"是什么"**——租户级字段库里的一份独立定义，与用在哪儿无关。
- **ContentType = 字段"怎么编排"**——隶属某个 Page，从字段库里挑一组字段组装成一种内容形态。

#### Field（独立定义表，租户级）

**Field 实现 `Dignite.Abp.FlexFields` 的 `IFlexField` 契约**（见 §8.2），属性与之一一对应：

| 属性 | 对应 `IFlexField` | 说明 |
|---|---|---|
| **Name** | `Name` | 租户内唯一标识，如 `title`、`body`、`cover`。**同时是值袋里的 key**——故改名是一次数据迁移，见 §2.4 |
| **DisplayName / Description** | 同名 | Description 同时是给 AI 的字段说明 |
| **FieldTypeName** | `FieldTypeName` | 字段类型的注册名，见下 |
| **Configuration** | `Configuration` | 类型特有配置（字符上限、可选项、媒体约束等），`FieldConfigurationDictionary` |
| **Group** | —（Sites 自有） | 可选。字段库的组织分组（≈ Cms `FieldGroup`），纯管理用途，不影响运行时 |

字段类型由 **FlexFields 内核的 `IFieldType` 提供**，内置六种（Text / Number / DateTime / Select / Boolean / Tree），Sites 按需自注册扩展类型（richtext / media / reference / list 等）——注册走 DI，不改内核。每个 `IFieldType` 自带 `IndexValueType`（`String / Number / DateTime / Boolean / Guid`，`null` = 该类型不可索引，如富文本），决定值落进查询索引的哪个类型化列，见 §2.4。

> **注**：字段类型抽象**不自建**。早期曾规划由 Sites 自己抽一层字段类型抽象（把 DynamicForms 验证过的模式吸收过来重写）——那层现已独立成 `Dignite.Abp.FlexFields` 模块并落码，Sites 直接消费即可。详见该模块的 `docs/flexfields-design.md`。

**一次定义、处处复用**：`title` 只在字段库里定义一遍，博客帖子、产品、新闻的 ContentType 都引入同一个 Field。改一处，所有引用它的类型同步——这正是独立定义表相对内联字段的核心价值。

#### ContentType（隶属 Page 的字段编排）

| 属性 | 说明 |
|---|---|
| **PageId** | **隶属的 Page**（≈ Cms `EntryType.SectionId`）。ContentType 建在 page 之下，不跨 page 共享 |
| **Name** | page 内唯一，如 `post-article`、`post-gallery`、`post-video` |
| **DisplayName / Description** | Description 同时是给 AI 的类型说明 |
| **引入的字段[]** | 有序引用列表，每项指向字段库里的一个 Field，见下 |

**引入的字段项**（≈ Cms `EntryField`）= 一个 `FieldId` 引用 + **本类型内的"用法"属性**：

| 用法属性 | 对应 | 说明 |
|---|---|---|
| **Required** | Cms `EntryField.Required`；FlexFields `FlexFieldValue.Required` | 本类型下该字段是否必填 |
| **Searchable** | Cms `EntryField.EnableSearch`；FlexFields `FlexFieldValue.Searchable` | 本类型下该字段的值是否拆解进查询索引表（见 §2.4） |
| **ShowInList** | Cms `EntryField.ShowInList` | 列表场景是否呈现该字段 |
| **DisplayName**（可选覆盖） | Cms `EntryField.DisplayName` | 不填则用 Field 自身的显示名 |
| **Order** | —（Cms 靠 Tab 内集合顺序，Sites 去 Tab 后显式给序号） | 在本类型内的顺序 |

> **为什么这些挂在引用上而不是 Field 上**：Field 描述字段的**固有性质**（类型、配置），跨类型恒定；Required / Searchable / 顺序 / 显示名描述的是**这次使用的意图**，天然随类型而变——同一个 `title` 在 `post-article` 必填可搜、在别处选填不索引，都正常。这既是 Cms `EntryField` 的切法，也正是 FlexFields `FlexFieldValue` 的切法（其 XML 注释明写 *"Per-usage rather than per-definition"*）。两边一致，沿用。

ContentType **不含路由、不含模板、不含基数标志**——那些是 Page 的事或运行时决定。它可以**引入一组标准 SEO 字段**（见 §5.3）。

> **与 Cms 的唯一差异：不设 `EntryFieldTab`。** Cms 里 EntryType 的字段先分 Tab 再列字段，那是后台表单的 UI 分组——Sites 主路径是 MCP、弱化后台表单，这层分组失去所指，且它让"类型有哪些字段"要穿两层集合才拿得到。ContentType 直接持有扁平的字段引用列表。已定。（FlexFields 内核对此无所谓：富页签布局本就归下游 UI。）

### 2.4 Content（内容记录）

一条内容 = **`PageId` + `ContentTypeId` + `CultureName` + 各字段的值**——结构完全对齐 Cms `Entry`（`SectionId` + `EntryTypeId` + `Culture` + 字段值），仅语言列改名，理由见下。**一条 Content 就是一个语言的一条记录**，多语言 = 多行。

- **归属 Page**：决定它落在哪条路由下、URL 前缀是什么。
- **归属 ContentType**：决定它有哪些字段、渲染成哪种形态。
- **两个归属都显式持有**：`PageId` 虽可从 `ContentTypeId` 推导（ContentType 已隶属 Page），但仍冗余存一份——按 page 拉内容是最高频查询（列表页、sitemap、路由解析），不该每次都绕一跳。Cms 的 `Entry` 同样两个都存，沿用。
- **系统字段有四个**：`CultureName`（本行是哪个语言）、`Slug`（路由解析的 key）、`status`（草稿 / 发布 / 归档）、`PublishTime`（发布时间，与 status 配合实现**定时 / 自动发布**——到点由后台作业把草稿转为已发布）。加 ABP 审计字段（创建 / 修改时间与人，自动带）。
- **业务字段**：全部来自其 ContentType 引入的 Field——包括 Title、SEO、正文，一切展示性数据。值全部落在本行自己的值袋里（见下），**不存在"跨语言共享的字段值"**：非本地化字段在各语言行里各存一份。
- **多语言分组靠自然键，不设分组 Id**（已定）：`(PageId, ContentTypeId, Slug)` 相同、`CultureName` 不同的若干行，**天然就是同一条内容的各语言版本**。hreflang（§5.5）与语言切换直接按这个自然键聚合派生，无需额外的 `TranslationGroupId`——Cms 没有分组机制，Sites 也不加。

> **代价要认**：分组键含 `Slug`，等于**要求同一条内容的 slug 跨语言一致**（`/en/blog/my-trip` 与 `/zh/blog/my-trip`），不能给中文版单独起一个本地化 slug。换来的是零额外实体、零额外外键，分组关系永远不会与数据脱节。

#### 语言列为什么叫 `CultureName`（已定）

Cms 叫 `Entry.Culture`，Sites 改叫 `Content.CultureName`。这是**唯一一处对 Cms 结构的命名修正**，理由三条：

- **对齐 ABP 自己的先例**：`Volo.Abp.LanguageManagement.Language` 实体的字符串属性就是 `CultureName` / `UiCultureName`。ABP 的模式是"概念叫 Language，存字符串的属性叫 CultureName"。Sites 的语言清单本就从 ABP 设置 / LanguageManagement 读，同名 = 读出来直接用，零转换。
- **类型诚实**：它是 `string`，装的是 `CultureInfo.Name` 的值，不是 `CultureInfo`。裸叫 `Culture` 在 .NET 里读起来像是后者——ABP 凡存字符串处一律加 `Name` 后缀正是为避此歧义。
- **不与 ABP `Language` 实体撞名**：若叫 `Content.Language`，同一解决方案里它是 string、`Language` 却是聚合根，读代码时容易错位。

**值域约定（硬约定）**：存 **`CultureInfo.Name` 形式的 BCP 47 标签**——`en`、`zh-Hans`、`en-GB`，大小写与分隔符严格照 .NET 的规范形式。

> 这条必须钉死：同一个值同时充当 **URL 前缀**、**hreflang 属性值**和**唯一键与分组键的一部分**，三者对格式的容忍度不一样。一旦出现 `zh-CN` 与 `zh-cn` 各存一行，唯一约束拦不住（多数排序规则下二者不等），分组就会从中间裂开，hreflang 随之输出两组互不相认的链接。写入口（MCP / 后台）统一过 `CultureInfo.GetCultureInfo(x).Name` 规范化后再落库。

> **系统字段 vs 业务字段的划分标准**：系统字段 = 平台机制**铁依赖**、不可能交给业务自定义的（Slug 支撑路由、status 支撑发布流程、PublishTime 配合 status 支撑定时发布）；业务字段 = 展示性数据（Title、SEO……）。凡是"某个类型需要、另一个类型不需要"的，都归业务字段。

#### 值怎么存：FlexFields 的 Y 方案（已定）

字段值**不自建存储方案**，直接采用 `Dignite.Abp.FlexFields` 已落码的 Y 方案（见该模块 `docs/flexfields-design.md` §4）。它是**权威值袋 + 派生索引表**两层：

| 层 | 落在哪 | 职责 |
|---|---|---|
| **权威值袋** | Content 实体自己的 `FlexFields` 字典列（`Content : IHasFlexFields`） | 唯一事实来源。整条内容读取只查这一处，一次拿全 |
| **派生查询索引** | 独立的 `ContentFlexFieldIndex` 表（Sites 自有，继承内核的 `FlexFieldIndexBase<Content>`） | 只为"找出字段 X 匹配 Y 的内容"能走 SQL 而非内存过滤 |

**权威值袋**是 FlexFields 自建的 `FlexFieldDictionary`，**不是 ABP 的 `ExtraProperties`**——刻意与公共大袋子隔离，防撞名、平台自持。

- **袋子的 key 是 `Field.Name`**（不是 Id）。所以**字段改名是一次数据迁移，不是一次简单编辑**：内核给了 `IFlexFieldValueMigrator<Content>`（provider 中立、唯一实现、下游零代码），改完定义后调 `RenameFieldAsync(oldName, newName)` 重写袋子 key。删字段同理。
- **索引行的键是 `FieldId`**（不快照字段名）——所以纯改名对索引无害，索引不需要跟着迁移。两层的键刻意不同，这是设计的一部分。

**派生索引表**每宿主类型一张，Sites 只需要 `ContentFlexFieldIndex` 一张：

- 行结构 = `FieldId` + `ValueType` + **五个类型化槽位**（`StringValue` / `NumberValue` / `DateTimeValue` / `BooleanValue` / `GuidValue`）+ Sites 自己声明的 `ContentId` 外键。数字进数字列、日期进日期列，**不 stringify**，比较走原生类型。
- **只索引 `Searchable` 的用法**（§2.3 引用行那个开关）；字段类型的 `IndexValueType` 为 `null` 者（如富文本）根本不可索引。
- **写时同 UoW 同步**：值一变，索引在同一个事务里跟着更新，不存在读到陈旧索引。
- 查询路径：条件 → 索引表 → `ContentId` → 回宿主过滤。`FlexFieldQueryCondition` 自带 `ValueType`，查询侧自描述、不回查定义。
- `Searchable` 翻开 / 字段类型改动都只需 `RebuildAsync` 全量重推——索引每次都从袋子里的原始值重新解释，没有独立的值迁移。

> **这一步直接治掉了 Cms 的老毛病**：Cms 的值存在 `ExtraProperties` JSON 里，`EfCoreEntryRepository.GetListAsync` 一旦带自定义字段条件就 `AsEnumerable()` 拉进内存过滤，数据量一大就是全表扫。类型化索引表让同样的查询回到 SQL 侧走索引。

> **provider 中立**：上述透视表形状只属于 `FlexFields.EntityFrameworkCore`。若将来走 MongoDB，内核直接在值袋上建原生路径索引、无透视表，写时近乎零同步——Sites 这一层的设计不用改。

### 2.5 关系与约束

- **Page → ContentType**：一对多**隶属**（ContentType 持 `PageId`）。类型建在 page 之下，删 page 即连带其类型；**类型不跨 page 复用**。
- **ContentType → Field**：多对多**引用**（经引用行，带 Required / DisplayName / Order 覆盖）。一个 Field 可被任意多个 ContentType 引入——**跨 page 的复用只发生在这一层**。
- **Content → (Page, ContentType)**：双重归属，各指一个；两者必须自洽（`Content.PageId` == 其 `ContentType.PageId`）。
- **Field → 值**：权威值按 **`Field.Name`** 存在 Content 的值袋里（故改名要迁移）；派生索引行按 **`FieldId`** 关联（故改名不影响索引）。两层键不同是刻意的，见 §2.4。
- **唯一约束**：`(租户, PageId, CultureName, Slug)` 唯一——同一 page 下、同一语言、slug 不重复（对齐 Cms 的 `SlugExistsAsync(culture, sectionId, slug)`）。
- **多语言分组**：`(PageId, ContentTypeId, Slug)` 相同、`CultureName` 不同 = 同一条内容的各语言版本。**自然键分组，不设分组 Id**；代价是 slug 跨语言一致，且 `CultureName` 必须规范化存储，均见 §2.4。

### 2.6 一个完整例子

一个公司官网：首页 + 关于我们 + 博客（帖子分图文 / 相册 / 视频三种形态）。

**① Field（字段库，租户级——先定义一次，后面反复引用）**

| Field | 类型 | 说明 |
|---|---|---|
| `title` | text | 标题 |
| `body` | richtext | 正文 |
| `cover` | media | 封面图 |
| `gallery` | list | 图集（多图） |
| `video-url` | text | 视频地址 |
| SEO 字段组 | 预设的一组 | 标准 SEO 字段组预设，见 §5.3 |

**② Page → ContentType（类型建在各自 page 之下，从字段库引入字段）**

| Page | Route | 内容路径模式 | 下辖 ContentType | 引入的字段 |
|---|---|---|---|---|
| 首页 | `/` | —（就一条，slug 空） | `home` | `title`、`body`、`cover` |
| 关于 | `/about` | —（就一条，slug 空） | `about` | `title`、`body` |
| 博客 | `/blog` | `{slug}` | `post-article` | `title`、`cover`、`body` + SEO 组 |
| | | | `post-gallery` | `title`、`cover`、`gallery` + SEO 组 |
| | | | `post-video` | `title`、`cover`、`video-url` + SEO 组 |

注意 `title` / `cover` / `body` 在五个类型里**是同一个 Field**，各自只在引用上设不同的 Required 与顺序。想给全站标题加个字符上限，改字段库那一处即可。三个博客类型都隶属 `/blog` 这个 page，不会（也不需要）被别的 page 借用——**跨 page 复用的是字段，不是类型**。

**运行时 URL**
- `/` → 首页 page 下那条 `home` 内容 → 前端渲染单页
- `/about` → 关于 page 下那条 `about` 内容 → 单页
- `/blog` → 博客 page 本身 → 前端渲染列表（自己拉它下面的内容）
- `/blog/my-trip` → 博客 page 下 slug=my-trip 的内容 → 前端按它的 ContentType（比如 `post-gallery`）选相册模板渲染详情

新增一条博客内容并发布，它的详情 URL 自动出现、sitemap 自动收录——不需要动任何 page。这就是"一切皆 page"和"page 即路由"的兑现。

## 3. 路由与 URL

### 3.1 Page 是权威路由表

后端的 Page 集合（连同其下 Content 的 slug）就是这张路由表：行是运行时数据，用户 / AI 新增一条内容即新增一条路由，无需重新编译或重启。前端就算自带路由，这张表也必须在后端存在——sitemap / canonical / hreflang 都从它算。

### 3.2 URL 构成

**URL = page 路由 + 内容 slug（若非空）**。单页和列表由此统一，不需要 Kind：

| URL | 解析 | 前端渲染成 |
|---|---|---|
| `/about` | `about` page 下那条 slug 为空的内容 | 单页 |
| `/blog` | `blog` page 本身 | 列表 |
| `/blog/my-post` | `blog` page 下 slug=my-post 的内容 | 详情 |

### 3.3 内容路径模式

Page 上一个可选的"内容路径模式"决定其下内容的 URL 怎么拼：
- 默认 `{slug}` → `/blog/my-post`
- 带日期段 `{date:yyyy/MM}/{slug}` → `/news/2026/07/my-post`

这属于**路由**（page 的职责），与"是否单页 / 列表"无关，因此不违背"不预设 Kind"。表达方式对齐 Dignite.Cms。

### 3.4 路由解析流程

请求进来：**域名 → 租户/站点**（ABP Domain Tenant Resolver，见 §4）→ 用路径匹配 page 集合：

1. 精确匹配基础路由（如 `/about`、`/blog` 本身）；
2. 前缀 + 路径模式匹配（如 `/blog/my-post` → 命中 `/blog` page，余下部分按路径模式解析出 slug）→ 按 `(PageId, CultureName, Slug)` 取内容——正是 §2.5 那条唯一约束，命中至多一条；
3. 都不中 → 查重定向表 → 否则 404。

**渲染交前端**：后端解析出"命中了哪个 page / 哪条内容、它是什么 ContentType"，前端决定渲染成单页还是列表、用哪套模板。后端不预设页面形态。

## 4. 站点配置（无 Site 实体）

早期设计里的 `Site` 聚合**已移除**。域名、语言、状态、主题、统计 ID、robots 策略等本质都是**设置项**，走 ABP 的能力即可，不必为它们立一个聚合。

### 4.1 走 ABP Settings（租户级）

语言、默认语言、主题、统计 ID、robots 策略、默认 OG 图、标题模板等 → **租户级 ABP Settings**。多租户隔离由 ABP 原生提供，A 租户的设置绝不串到 B。

### 4.2 域名 → Domain-Names 模块

域名是唯一的例外：它不是"取当前租户的设置"，而是"**给定 host 反查是哪个租户**"（反向解析），纯 Settings 做不了。这落到 Dignite 生态**现成的 Domain-Names 模块**——host→tenant 的映射与解析。每站点一个主域名，副域名整站 301 到主域（多租户头号 SEO 坑：自定义域 vs 平台子域重复内容，见 §5）。

### 4.3 一租户一站点

- **一租户 = 一站点**。移除 Site 实体后此结论依然成立：租户就是站点，站点配置就是租户设置。
- **host 主站** = 无租户上下文（TenantId 为空）的那套设置，与租户站同构，无需特例代码。

## 5. 站点级派生能力（SEO / sitemap / 可发现性）

> 本章吸收自原《03-网站功能整合规划》，按 2026 现状核对，关键 footgun 已标。这些能力都是**从 Page 路由结构 + Content 存在性派生**、平台按"域名→租户"解析后自动产出的，**依赖路由、不依赖具体 SEO 字段值**——所以 SEO 字段下放到 ContentType（§5.3）不影响它们。

### 5.1 四条平台原则

普通建站工具让用户手填 SEO；Sites 的每个功能都满足：
1. **每租户可配 + 平台有合理默认**——不配也开箱达标；
2. **模板 / 派生自动产出**——非技术用户零操作即获得（canonical、sitemap、JSON-LD）；
3. **严格命名空间隔离**——租户间 sitemap / robots / 统计绝不串；
4. **AI 优先生成**——AI 既然已写内容，就顺手生成 meta、alt、结构化数据、hreflang、首段直答。

> 适用范围：以上"开箱达标"保证覆盖平台官方骨架（Tier 0，见 §7）。外部前端（Tier 1/2）需自行满足一致性清单。

### 5.2 sitemap（必备）

- 发布 / 变更时，从 **Page + Content** 生成：所有基础路由 page + 每个 page 下每条已发布内容展开的 URL。
- **[footgun] lastmod 只在内容真变时更新**——若全站都盖"今天"，Google 会**全站忽略**该字段。用内容的实际更新时间 / 内容哈希驱动。
- 单文件上限 5 万 URL / 50MB；实践按 **1–2 万 / 文件**分片 + gzip，按类型分片（pages / news / products）+ 每租户一个 sitemap index。
- 采用 **X.Web.Sitemap**（自动分片 + 索引），只写"从库里喂 URL + 分片键 + lastmod"这层胶水。

### 5.3 SEO（<head> 元数据 + 路由派生）

SEO 分成两半，各归其位：

**① 影响单页 `<head>` 的元数据 → ContentType 引入的字段。**
meta title / description、og:image、noindex 等，本就是"这条内容的元数据"，和正文一样，走普通字段机制、值存 Content、分语言。平台在**字段库里预置一组标准 SEO 字段**（§2.3 的 Field，租户开箱即有），带平台能识别的语义（例如 `noindex` 一旦有值，sitemap 就不收这条 URL）。ContentType 按需引入这组：引了就有平台级 SEO 能力（含 AI 自动填），不引走纯默认。

> 字段库独立成表在这里正好兑现：SEO 字段组只定义一次，被多少个类型引入都是同一份定义——平台要识别 `noindex` 语义，认的是那个固定的 `FieldId`，不必在每个类型里按名字猜。

**② 从路由派生的产物 → 平台自动算。**
canonical（自指向主域绝对 URL）、hreflang、sitemap——平台从路由结构算，不读 SEO 字段。canonical 用 §4.2 的主域名生成；草稿 / 预览页强制 noindex。

标签输出复用 **`Dignite.Abp.Seo`（SeoTags + Schema.NET）**，几乎零新代码。

### 5.4 结构化数据 JSON-LD（必备核心类型）

**[变：2025–2026 富结果大幅缩水，只做还渲染的]**
- Organization / WebSite（全站发）、BreadcrumbList（路由生成）、Article / NewsArticle / Product+Offer（有效富结果）。
- ContentType 上加一行 `schemaOrg` 映射 + 字段映射，发布时自动产出 JSON-LD，发布前用 Rich Results 校验当闸门；AI 也可直接补全。
- **[footgun] FAQPage / HowTo 富结果已下线**（FAQ 2026-05 停、HowTo 2023 起无）——仍可发供 AI 解析，但别指望 SERP 下拉。
- **[变] Product 图**最小 500×500（2026-04 警告、2027-01 强制）。

### 5.5 多语言 hreflang（必备——多语言是核心设计）

- `hreflang` + `x-default` **由多语言分组自动生成**：按 §2.4 的自然键 `(PageId, ContentTypeId, Slug)` 聚合出同一内容的各语言行，取各行的 `CultureName` 直接作 `hreflang` 值（这正是它存 BCP 47 规范形式的原因之一），互指、自指、绝对 URL；`x-default` 指向中性首页。
- URL 策略默认**子目录 `/de/ /fr/`**（合并域名权重、最易自动化）；有法律 / 托管分离需求才用子域 / ccTLD。
- 我们"每语言一份记录 + 自然键分组"的模型，让 hreflang 几乎是免费副产品——一次 `GROUP BY` 就出，没有分组表要维护、也不会出现分组 Id 与数据脱节。
- **与子目录策略天然契合**：slug 跨语言一致（§2.4 的代价），各语言 URL 只差前缀（`/en/blog/my-trip` ↔ `/zh/blog/my-trip`），互指关系一眼可验。

### 5.6 robots + AI 爬虫开关（必备）

- `robots.txt` 每域名各自生成（按域名→租户解析）。
- **AI 爬虫开关**（当前唯一实用杠杆）：区分**训练类**（GPTBot / Google-Extended / ClaudeBot / CCBot）与**搜索/RAG 类**（OAI-SearchBot / PerplexityBot / Claude-SearchBot），每租户可分别开关。常见策略：放搜索、挡训练。
- `llms.txt` 低 ROI（约 10% 采用、Google 明确不支持），廉价自动生成、标为可选，不当排名手段。

### 5.7 重定向 / 错误 / TLS（必备）

每租户 `Redirect` 规则：301/302、改 slug 自动建 301、扁平化避免重定向链、品牌化**真 404**（避免 soft-404 返回 200 的模板陷阱）、HTTPS + 自定义域自动签证书（ACME / Let's Encrypt）+ HSTS。自建薄层（RewriteMiddleware + 每租户重定向表）。

### 5.8 性能 / Core Web Vitals（必备）

**[变：当前三指标 = LCP / INP / CLS；INP 2024-03 取代 FID]**，取 CrUX P75。
| 指标 | 良好阈值 | 备注 |
|---|---|---|
| LCP | ≤2.5s | |
| INP | ≤200ms | **2026 最常挂的指标**（约 43% 站点不达标） |
| CLS | ≤0.1 | 媒体 / 嵌入预留尺寸 |

支撑项（模板 / CDN 层）：AVIF/WebP + 响应式 srcset、below-fold lazy（LCP 图除外）、图片显式 width/height 防 CLS、LCP 图 fetchpriority=high、关键 CSS 内联、字体 font-display:swap、BLOB + CDN / 边缘做缩放与格式协商。

### 5.9 社交 / feed / 分析 / 无障碍

- **社交**：Open Graph（og:image 1200×630、<1MB、居中安全区）、Twitter summary_large_image、favicon 全套 + webmanifest。
- **feed**（博客近必备）：RSS / Atom 自动生成（`<link rel=alternate>` 自发现），数据源同为 Content。采用 `System.ServiceModel.Syndication` + `JsonFeed.NET`。
- **分析与隐私**：每租户统计 ID（GA4 / Plausible），Tag 容器隔离；GDPR Cookie 同意 + Google Consent Mode v2，同意前拦截非必要 tag。
- **无障碍**：WCAG 2.2 AA 基线（alt、label、对比度、焦点、跳转链接），AI 生成 alt 文本。搜索结果页 noindex。

## 6. AI / MCP 能力面

### 6.1 理念

平台把能力**开放为 MCP**，不内嵌后台助手。用户在自己的 AI 客户端里完成两类工作：
- **建站期**：口述创建 page（定路由）、在 page 下建 ContentType 并引入字段（字段库里没有就顺手新建 Field）、填充 Content（填内容），甚至构建前端模板。
- **运维期**：口述发布 / 修改内容（"发一条新闻，正文如下……"），AI 客户端调 MCP 工具，平台按字段定义校验、入库，路由与 sitemap 自动更新。

`schema 即契约`在这里兑现：ContentType 引入的那组 Field 就是 AI 生成内容的目标形状，也是写入校验闸门；AI 顺手产出的 SEO 字段（meta / alt / JSON-LD / 首段直答）同样过闸门。

### 6.2 工具面（待细化）

MCP 具体暴露哪些工具、怎么切分（按实体？按场景？读写分离？权限？）**留待后续专门讨论**。当前先把结构定稳，工具面在结构之上设计。

## 7. 前端架构（混合无头）

> 本章吸收自原《06-开放式前端架构》。方向：前端不锁定语言 / 框架，官方提供配套骨架，开发者也可贡献前端。与内容内核（§2）正交——内核不因前端选择而改。**部分细节仍是探索方向，待拍板项见 §10。**

### 7.1 混合无头

官方骨架与任意技术栈的外部前端并存，共享同一套内容内核（先例：Shopify 的 Liquid 托管主题 + Storefront API 外部前端并行多年）。设计收在两条原则上：渲染引擎只新增 **Scriban** 一个变量；契约克制（后端只暴露一小撮稳定通用的原语）。

### 7.2 Razor 归 ASP.NET Core，Scriban 是唯一新增

- 需要 Razor 时，**直接用 ASP.NET Core 原生的 MVC View / Razor Page / Blazor**——编译期检查、IntelliSense、调试、TagHelper 一样不少，不必借 ABP TextTemplating 包一层。
- **Scriban 存在的唯一理由是安全**：它是唯一可以放心交给租户 / AI 直接写、不担心执行任意代码的引擎。

| | 谁写 | 用什么渲染 | 能否被租户/AI 改 |
|---|---|---|---|
| 平台固定页面 / 组件 | 开发者 | ASP.NET Core 原生 Razor | 否——编译产物，走发布流程 |
| 租户 / AI 内容槽 | 租户或 AI | **Scriban**（沙箱） | 是——数据，不经编译，覆盖即生效 |

### 7.3 三层前端

| 层级 | 例子 | 与内核的关系 | SEO / SSR 责任 |
|---|---|---|---|
| **Tier 0 同进程动态骨架**（推荐 ASP.NET Core MVC） | MVC catch-all + Scriban 内嵌 | 直接调 Application Service，无 HTTP 往返 | 平台保证（§5 四原则在此兑现） |
| **Tier 1 跨进程动态骨架** | Next.js、Astro、独立 ASP.NET | 经 Delivery API（只读、只出已发布、版本化）读写 | 前端自负，平台给一致性清单 |
| **Tier 2 纯静态资源托管** | 用户上传的静态 HTML/CSS/JS | 不涉及内核，走 BLOB 托管 | 前端自负，平台不介入 |

MVC 的 `MapControllerRoute` `{*path}` catch-all 能对接运行时可变的路由（路由集合是数据，不是编译期常量），是 Tier 0 的自然选择。

### 7.4 动态路由表 = Page / Content 索引 + resolve-path 契约

"服务器端动态路由表"不是新组件——就是 §2 的 Page / Content 表。真正新增的只是一个契约动作：`resolve-path(path) → { matched, template, engine }`。Tier 0 里是进程内查询；Tier 1 里是 Delivery API 的一个端点——同一张表，两种触达。

### 7.5 安全边界

**凡"Razor"一律平台 / 开发者专属、走编译管线；凡需租户 / AI 写，一律落 Scriban，没有第二条路。** 允许租户内容进编译管线 = 允许其执行任意 C#，是远程代码执行，不是渲染。

Scriban 沙箱要点：`MemberFilter` 白名单只暴露公共属性，阻断方法调用与反射逃逸；默认无模板加载器（`include` 读不到文件系统）；循环上限 1000、递归上限 100；只暴露传入模型、全局字典与本地化助手。

## 8. 技术选型（Build vs Adopt）

> 本章吸收自原《04-技术选型》。**原则**：优先复用成熟、维护良好、许可证兼容的开源库；能复用 Dignite 自有模块最优先；只有现成轮子不合适、或与多租户 / AI 核心诉求冲突才自建，且自建尽量做薄。每引入依赖检查三件事：许可证兼容、近一年有维护、非单点维护。

### 8.1 决策顺序

先看 Dignite.* 自有 → 再看 ABP / 生态 → 再看通用 .NET 开源库 → 都不合适才自建（薄胶水层）。

### 8.2 复用 Dignite 生态（最大杠杆）

| 自有模块 | 能力 | 对 Sites 的意义 |
|---|---|---|
| **Dignite.Abp.FlexFields** | 字段类型抽象（`IFieldType` × 6 内置 + DI 扩展）、值袋（`IHasFlexFields`）、派生索引与查询下推、校验、改名迁移 | **整个字段体系的底座**。Sites 只出 `Field : IFlexField`、`Content : IHasFlexFields`、`IFlexFieldProvider<Content>` 和一张索引表，机制全由内核给 |
| **Dignite.Abp.Seo** | SeoTags（meta/OG/Twitter/canonical）+ Schema.NET（JSON-LD） | SEO 标签直接复用，几乎零新代码 |
| **Dignite.Cms** | 无头、可定义字段、多租户 / 多站点 / 多语言 / 版本化 | 内容内核的 DNA 来源（Sites 是其下一代） |
| **dignite-abp 单仓** | File Management（BlobStoring）、Themes、多租户 Localization、**Domain-Names**、Regionalization | 媒体、主题、多语言、**域名→租户**全是现成件 |

### 8.4 许可证红线（开源项目硬约束）

### 8.5 自建的薄层

## 9. 路线图

> 吸收自原《05-演进策略》。Dignite.Cms 无生产数据，仅作参考，**无需迁移工具**。

- **P0 内容内核**：Page / ContentType / Content 三实体 + Field 字段库（独立定义表）+ **接上 FlexFields**（`Field : IFlexField`、`Content : IHasFlexFields`、`IFlexFieldProvider<Content>`、`ContentFlexFieldIndex` 一张索引表、DbContext 里三个 `ConfigureFlexField*()`）+ 多租户隔离 + 多语言（跑通"博客单页 / 列表 / 详情"）。
- **P1 站点层**：Dignite.Abp.Seo 接入 + X.Web.Sitemap + robots + hreflang + Domain-Names 域名解析 + 主题 + Tier 0（MVC catch-all + resolve-path + Scriban 内嵌）。
- **P2 AI / MCP**：MCP 能力面落地——AI 客户端口述建 page / 定字段 / 发内容 + 顺手生成 SEO 字段（核心卖点）。
- **P3 替换 Cms**：Dignite.Cms 进入维护模式，README 指向 Sites；对外信息为"Cms 的 AI 原生下一代"，避免生态分裂。
- **P4 增强**：feed、站内搜索、AEO / GEO 工具、更多 schema、套餐分级（ABP Feature / Edition）、Tier 1 Delivery API + 第一个外部 starter（Next.js 或 Astro）。
